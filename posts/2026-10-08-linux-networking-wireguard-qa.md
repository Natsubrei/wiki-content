## 引子

我在一个 Kubernetes 集群上做了一件小事：把集群里随机分配的 NodePort 暴露到公网。

做完之后，内网的网页打不开了。排查过程中我被问了一连串问题，从「dport 是什么」问到「WireGuard 会把 UDP 转成 TCP 吗」。

这些问题看起来零散，其实是一条链。本文按由浅入深的顺序把那串问答整理出来。每个术语第一次出现时都会解释。

文中地址全部是示例地址。`203.0.113.0/24` 是专门留给文档使用的网段，`10.99.0.0/24` 是示例中的隧道网段。

---

## 第一部分：Linux 怎么处理一个网络包

### 问题 1：一个包进了 Linux，先发生什么？

内核收发包要过五个固定关卡。这些关卡统称 **netfilter 钩子**。netfilter 是 Linux 内核里处理包的框架。

收包方向：

```text
网卡收到包
  → PREROUTING        包刚进来，还没决定给谁
  → 路由判定          看目的地址，决定是本机的还是别人的
      ├─ 是本机   → INPUT    → 交给本机进程
      └─ 是别人   → FORWARD  → 继续转发
  → POSTROUTING       快要出网卡了
  → 网卡发出
```

发包方向：

```text
本机进程
  → OUTPUT            → 路由判定 → POSTROUTING → 网卡发出
```

「路由判定」是这五个关卡中间的一步。它做的事是：拿包的目的地址去查路由表，然后决定这个包是给本机，还是转发给别人。

### 问题 2：DNAT 为什么必须放在路由判定之前？

**DNAT** = Destination NAT，改目的地址。

因为 DNAT 会改目的地址，而路由表要按改完之后的地址来查。如果 DNAT 放在路由判定之后，包已经被认定是「给本机的」，就转不出去了。

举个真实的例子。一个包到达入口节点，目的地址是 `10.99.0.2`。这个地址是节点自己的，正常会被送去本机进程。但是：

```text
1. nat PREROUTING 先跑
   kube-proxy 的规则把它改掉
   10.99.0.2:31981  →  10.244.2.5:22

2. 然后路由判定才跑
   按新地址 10.244.2.5 查表，发现这个 Pod 在另一台节点
   → 走 Calico 隧道，发给 10.10.1.11
```

如果顺序反了，这个包永远到不了 Pod。

改地址的两类动作，摆放位置是固定的：

| 动作 | 含义 | 放在哪里 |
| --- | --- | --- |
| DNAT | 改目的地址 | PREROUTING 或 OUTPUT |
| SNAT / MASQUERADE | 改源地址 | POSTROUTING |

### 问题 3：dport 是什么？

- `dport` = destination port，目的端口
- `sport` = source port，源端口

iptables 里的写法：

```bash
-p tcp --dport 31981
```

意思是「TCP 包，目的端口是 31981」。

这里有个关键点：**kube-proxy 的 NodePort 规则只看端口，不看目的地址**。所以 `10.99.0.2:31981` 和 `10.10.1.10:31981` 命中同一条规则。

这一点后面会反复用到。

## 第二部分：虚拟网卡

### 问题 4：wg0 是什么？网卡可以是软件造出来的吗？

可以。`wg0` 不是真实网卡，是软件造出来的。内核把它当成一块普通网卡对待。

```bash
ip link show wg0
# 119: wg0: <POINTOPOINT,MULTICAST,NOARP,UP,LOWER_UP> mtu 1420
```

注意两个标志：

- `POINTOPOINT`：点对点。这条「线路」对面只有一个对端。
- `NOARP`：不做 ARP。不需要靠 MAC 地址找人。

它没有 MAC 地址。这不是缺陷，是设计。

### 问题 5：以太网头是干什么的？

以太网头只有三个字段，各自解决一个问题：

| 字段 | 作用 | 为什么需要 |
| --- | --- | --- |
| 目的 MAC | 指明这一跳谁收 | 网线或 Wi-Fi 是共享的，上面有很多设备 |
| 源 MAC | 指明谁发的 | 对方回包用 |
| EtherType | 载荷是 IPv4、IPv6 还是 ARP | 接收方要知道交给哪个协议处理 |

根本原因：**一条链路上有多个设备，要靠 MAC 地址选出下一跳**。

### 问题 6：那 wg0 为什么不需要 MAC 地址？

三个原因。

**一、没有「多个设备」需要区分。**

`wg0` 是点对点隧道。它的对面是谁，不靠 MAC，靠配置里的 `AllowedIPs`：

```ini
[Peer]
PublicKey = ...
AllowedIPs = 10.99.0.1/32
```

内层包的目的 IP 是 `10.99.0.1`，WireGuard 查 `AllowedIPs` 就知道该加密给哪个对端。这相当于自己做了一次「下一跳选择」，所以不需要 MAC，也不需要 ARP。

**二、不需要 EtherType。**

`wg0` 上跑的全是 IP 包。接收方看包的第一个字节里的版本号（4 或 6）就能分辨 IPv4 还是 IPv6。

**三、没有物理介质的约束。**

帧间隔、填充到最小长度、校验尾（FCS）都是物理线路的需要。`wg0` 是纯软件，不存在这些问题。

对照表：

| | 二层设备 | 三层设备 |
| --- | --- | --- |
| 例子 | eth1、veth、bridge、tap | wg0、tun |
| 收发内容 | 带以太网头的帧 | 纯 IP 包 |
| 需要 MAC / ARP | 是 | 否 |
| `ip link` 显示 | `link/ether` | `link/none` |
| 路由写法 | 常有 `via` 网关 | 只写 `dev` |

可以自己验证：

```bash
ip link show wg0      # link/none，没有 MAC
ip link show eth1     # link/ether xx:xx:xx:xx:xx:xx
tcpdump -i wg0 -e     # 看不到以太网头，直接是 IP 包
```

### 问题 7：那以太网头是消失了吗？

不是消失，是**内层不需要，外层照常有**。

```text
wg0 里的内层包：   [IP 头][数据]                        ← 无以太网头
                         ↓ 加密，作为 UDP 载荷
从真实网卡发出：   [以太网头][IP 头][UDP 头][加密载荷]   ← 这里才加
```

以太网头只在包真正进入以太网的那一刻才加。目的 MAC 是网关的 MAC。

WireGuard 的加密隧道本身就是一条「逻辑链路」，它自己就能点对点送达。所以内层不再需要以太网头。

### 问题 8：MTU 为什么是 1420？

**MTU** = Maximum Transmission Unit，一块网卡能发出去的最大包长。以太网的 MTU 通常是 1500。

`wg0` 是 1420，比 1500 小。差的那 80 字节被加密头和 UDP 头占走了。

内核看到 MTU 变小，会自动调小 TCP 的最大段长（MSS）。实测抓到的内层 MSS 是 1382。这样包不会被分片。

### 问题 9：TUN 是什么？发给它的包去哪了？

**TUN** 是一种由用户态程序充当对端的虚拟网卡。

内核里有一块名叫 `tun0` 的三层网卡。发给它的 IP 包不会送去硬件，而是交给某个进程读取。进程写回的 IP 包，内核当作「从这块网卡收到的」。

一句话：**TUN 是内核网卡和用户态进程之间的桥梁。**

对照几种网卡的「另一端」是谁：

| 网卡 | 发给它的包去哪 |
| --- | --- |
| eth0（物理） | 网卡硬件，变成电信号 |
| veth | 另一块 veth 网卡（常在另一个命名空间） |
| bridge | 按 MAC 转发给某个端口 |
| tun0 | 一个用户态进程，通过 `/dev/net/tun` 读取 |

工作流程：

```text
应用 ──→ 内核协议栈 ──→ 路由表：走 tun0
                         │
                         ↓ 放入发送队列
                    ┌─ /dev/net/tun ─┐
                    │  read()  ←─────┼── 用户态程序拿到一个 IP 包
                    │  write() ─────→┼── 程序写入一个 IP 包
                    └────────────────┘
                         ↓ 内核当作 tun0 收到的包
                    协议栈 ──→ 应用
```

用户态程序对这个设备只做两件事：`read()` 取包，`write()` 放包。取到包之后想干什么都行：加密、压缩、转发、改写。这就是各类 VPN 和代理软件的基础。

自己可以造一块：

```bash
sudo ip tuntap add dev tun0 mode tun
sudo ip addr add 10.9.0.1/24 dev tun0
sudo ip link set tun0 up
ip -d link show tun0      # 看到 link/none 和 tun 类型
```

程序打开 `/dev/net/tun`，绑定到 `tun0`，然后循环 `read()`。另开终端 `ping 10.9.0.2`，就能读到 ICMP 包。

这对应问题 6 的对照表：TUN 是三层设备，`ip link` 显示 `link/none`，路由里只写 `dev tun0`，不需要 `via`。

常见使用者：

- OpenVPN：用户态读 TUN，加密后经普通套接字发出
- Clash、sing-box 的 TUN 模式：创建 TUN 网卡接管流量，再交给代理核心
- `wireguard-go`、Tailscale：WireGuard 的用户态实现，用 TUN 作为接口

### 问题 10：TUN 和 TAP 差在哪？这两个名字是缩写吗？

严格说都不是缩写。两个名字是从英文单词借来的。

| 名字 | 来源 | 含义 |
| --- | --- | --- |
| TUN | tunnel（隧道）的前三个字母 | 在 IP 层建立隧道，把 IP 包交给用户态程序 |
| TAP | tap（分接），如 wiretap（搭线窃听） | 像在网线上接一个分接头，拿到完整的以太网帧 |

有些资料会写成 “network TUNnel” 和 “network TAP”。这是后人为了好记的解释，不是官方全称。Linux 内核文档只称它们为 TUN/TAP。

内核里它们是同一个驱动。设备文件都是 `/dev/net/tun`。创建时用不同标志区分：

```text
IFF_TUN   → 三层，读写 IP 包
IFF_TAP   → 二层，读写以太网帧
```

对照：

| | TUN | TAP |
| --- | --- | --- |
| 层级 | 三层 | 二层 |
| 读写内容 | 纯 IP 包 | 完整以太网帧 |
| 有 MAC / 需要 ARP | 否 | 是 |
| 典型用途 | 点对点 VPN、代理 | 桥接、虚拟机网卡、二层 VPN |

**TAP** 是二层设备。用户态程序读写的是完整以太网帧。所以凡是需要「假装成一块真正的网卡接入局域网」的场景，都用 TAP。

最常见的场景是虚拟机网卡。QEMU/KVM 给虚拟机提供的网卡，宿主机一侧通常就是一个 TAP 设备：

```text
虚拟机内部             宿主机
  eth0（虚拟网卡）
     │  以太网帧
     ↓
  QEMU 进程  ←→  tap0  ──→  网桥 br0  ──→  物理网卡  ──→ 局域网
```

虚拟机里的系统以为自己插着一块普通网卡，会发 ARP、DHCP 等二层广播。这些帧经 `tap0` 进入宿主机，再通过网桥与真实局域网连通。必须是 TAP 而不是 TUN，因为虚拟机发出的是带以太网头的帧。

其它场景：

- 二层 VPN（OpenVPN `dev tap`）：两端局域网被桥成同一个二层网络
- 网络模拟器（Mininet、GNS3）：用 TAP 把虚拟设备接到宿主机网桥
- 微虚拟机（Firecracker）：每个实例对应一个 TAP

怎么选：

| 需求 | 选择 |
| --- | --- |
| 给虚拟机提供网卡 | TAP |
| 需要二层广播、ARP、非 IP 协议 | TAP |
| 把两个局域网桥接成同一网段 | TAP |
| 点对点 VPN、代理、只转发 IP 流量 | TUN |
| 追求更低开销 | TUN |

### 问题 11：搭 VPN 时，工作在二层和三层有什么本质区别？

本质区别：二层 VPN 把对端接进同一个局域网，三层 VPN 把对端用一台路由器连起来。

| | 二层 VPN（TAP） | 三层 VPN（TUN） |
| --- | --- | --- |
| 隧道相当于 | 一根网线 / 一台交换机 | 两个网络之间的一条路由器链路 |
| 两端网段 | 同一个网段 | 不同网段 |
| 广播域 | 两端合并成一个 | 各自独立 |

拓扑：

```text
三层（路由）：
  局域网 A 192.168.1.0/24 ─ 路由器 ═══隧道═══ 路由器 ─ 局域网 B 192.168.2.0/24
  A 访问 B：IP 层查路由表 → 转发

二层（桥接）：
  局域网 A 192.168.1.0/24 ─ 网桥 ═══隧道═══ 网桥 ─ 局域网 B 192.168.1.0/24
  A 与 B 同属 192.168.1.0/24：直接 ARP、直接发帧
```

具体差异：

| 对比项 | 二层 | 三层 |
| --- | --- | --- |
| 隧道里传的 | 完整以太网帧 | 纯 IP 包 |
| 广播 / 组播 | 会穿过隧道 | 不穿过 |
| ARP、MAC | 需要，跨隧道解析 | 不需要 |
| 非 IP 协议 | 支持 | 不支持 |
| DHCP、Wake-on-LAN | 能跨隧道使用 | 需要额外配置 |
| 每包开销 | 多 14 字节以太网头，加上广播 | 较小 |
| 规模扩展 | 差，广播随节点增长 | 好，路由天然隔离 |
| 安全边界 | 弱，ARP 欺骗可跨站点 | 强，只有路由到的流量才过去 |

关键是**广播域的边界**：

- 三层：边界在隧道口。包在隧道口被路由器重新出发，MAC 地址换掉，广播到此为止。
- 二层：没有边界。两端共享一个广播域。所有二层行为原样跨站点生效，所有二层问题也原样跨站点。

什么时候必须用二层：

- 需要同网段才能工作的软件：某些集群心跳、虚拟机热迁移
- 要用到广播发现：打印机发现、Wake-on-LAN
- 远程机器需要从对端 DHCP 拿地址
- 承载非 IP 协议

绝大多数情况用三层：远程办公、访问内网服务、站点互联。WireGuard、IPsec 隧道模式、OpenVPN `dev tun` 都是三层。OpenVPN `dev tap`、L2TP、VXLAN 是二层。

**WireGuard 只支持三层。** 这是设计取舍：不要 ARP，不转发广播，实现简单，攻击面小。如果确实需要二层，常见做法是在 WireGuard 隧道之上再跑一层 VXLAN，让 WireGuard 负责加密，二层封装负责桥接。

默认选三层。只有当应用明确依赖「同网段 / 广播 / 非 IP 协议」时，才为二层的开销和较大的安全暴露面买单。

## 第三部分：WireGuard 的原理

### 问题 12：WireGuard 到底做了什么？

把一个 IP 包放进隧道，只做四件事：

```text
1. 加密      整个 IP 包加密
2. 加头      外面套一个 UDP 头和一个外层 IP 头
3. 发出      按 Endpoint 的地址发出去
4. 对端解密  收到后把原始 IP 包放回内核
```

一句话：**WireGuard 把「加密」做成了一块普通的虚拟网卡。**

进隧道的是一个 IP 包，出隧道的还是那个 IP 包。其余全部交给 Linux 原有的网络栈。

### 问题 13：WireGuard 会把 UDP 包转成 TCP 吗？

不会。它不做任何协议转换。里层是什么协议，出来还是什么协议。

抓包可以证明。同一个 TCP 握手，在隧道内外长这样：

```text
=== wg0（隧道里面，已解密）===
10.99.0.1.40759 > 10.99.0.2.30080: Flags [S]      TCP SYN
10.99.0.2.30080 > 10.99.0.1.40759: Flags [S.]     TCP SYN-ACK
10.99.0.1.40759 > 10.99.0.2.30080: Flags [.]      TCP ACK

=== 真实网卡（隧道外面，已加密）===
203.0.113.10.51820 > 10.10.1.10.42775: UDP, length 96
10.10.1.10.42775 > 203.0.113.10.51820: UDP, length 96
203.0.113.10.51820 > 10.10.1.10.42775: UDP, length 96
```

两个结论：

- 里层仍是 TCP，端口仍是 30080。协议没有被换掉。
- 外层全是 UDP，端口 51820。

还有第二个证据：外层长度全是 96 字节。里层的 SYN 带选项，ACK 不带，长度本来不同。加密后长度变成一样，说明内容被藏起来了。

### 问题 14：那外层为什么用 UDP 而不是 TCP？

**如果 TCP 装进 TCP，两层都有自己的重传。** 丢一个包，两层一起重传，会指数放大，连接卡死。这个问题有个专名叫 TCP-over-TCP meltdown。

WireGuard 的外层固定用 UDP，就是为了避开它。

所以隧道上完全没有 TCP 握手，也不占用任何 TCP 端口。防火墙只需要放行一条 UDP 规则。

### 问题 15：AllowedIPs 是干什么的？为什么说它一张表两个用途？

```ini
[Interface]
PrivateKey = <本机私钥>
Address = 10.99.0.1/24

[Peer]
PublicKey = <对端公钥>
Endpoint = 203.0.113.10:51820
AllowedIPs = 10.99.0.2/32
```

| 方向 | 作用 | 类比 |
| --- | --- | --- |
| 发送 | 按目的 IP 选出用哪个对端的密钥加密、发到哪个 Endpoint | 路由表 |
| 接收 | 解密后检查内层源 IP 是否属于该对端，不符就丢弃 | 防火墙 |

接收那一步很关键。这是防伪造。就算攻击者拿到某个对端的密钥，也只能冒充那个对端 `AllowedIPs` 范围内的地址，没法伪造其他地址的包。

一个实用建议：**`AllowedIPs` 只写对端的隧道地址，不要写 `0.0.0.0/0`**。写 `0.0.0.0/0` 会把默认路由抢过去，所有流量都走隧道。除非你就是要做全局代理。

### 问题 16：加密是怎么做的？

| 项目 | 做法 |
| --- | --- |
| 身份 | 每个节点一对 Curve25519 密钥。对端用公钥标识，像 SSH 的 authorized_keys |
| 握手 | 基于 Noise 协议（Noise_IKpsk2），一来一回两个消息建立会话密钥，有前向安全性 |
| 数据加密 | ChaCha20-Poly1305，同时完成加密和认证 |
| 换密钥 | 会话密钥约每 2 分钟自动轮换，旧密钥作废 |
| 静默 | 不发数据就不发包。对未认证的陌生包不做任何回应，端口扫描发现不了 |
| 漫游 | 收到合法包时自动更新对端 Endpoint。换网络后连接自己恢复 |

漫游这一条很实用。笔记本从 Wi-Fi 切到 4G，对端的 Endpoint 会自动更新，连接不断。

### 问题 17：内核版和用户态版有什么区别？

两者对外看起来很像，都是三层设备。实现不同。

| | 内核版 `wg0` | 用户态版（`wireguard-go`） |
| --- | --- | --- |
| 实现 | 内核模块 | 普通程序 |
| 设备怎么来的 | 内核直接造一块网卡 | 程序开一个 TUN 设备（问题 9） |
| 加解密在哪 | 内核里 | 用户态进程里 |
| 包的路径 | 网卡 → 直接在内核加密 | 内核 → `read()` 拷贝到用户态 → 加密 → 再 `send()` 回内核 |
| 开销 | 小 | 多两次内核/用户态切换和拷贝 |
| 适用 | Linux 5.6+ | macOS、Windows、没有内核模块的系统 |
| 对用户 | 都是一块普通网卡 | 都是一块普通网卡 |

用户态版收发数据的过程：

```text
出方向
  内核把目的地在 AllowedIPs 里的包交给 wg0（TUN）
  wireguard-go 读走 → 加密 → 用 UDP 套接字发出

入方向
  wireguard-go 从 UDP 套接字收到 → 解密 → 把明文包写回 TUN
  内核认为「从 wg0 收到一个普通 IP 包」
```

内核版快，不是因为算法不同，而是省掉了 TUN 这条用户态往返路径。问题 4 说过：软件只要实现内核要求的网卡接口，内核就把它当网卡用。`wg0` 可以在发送函数里直接加密并调用 UDP 套接字，不需要借道用户态。

什么情况下必须用用户态版：内核没有 `wireguard` 模块，软件仓库里也没有 `wireguard-tools`。有些发行版的内核就是这样。macOS 和 Windows 也只能用用户态版。

## 第四部分：实现细节与术语

### 问题 18：`wg` 命令和 netlink、RTNL 是什么关系？

这几个词经常出现在 WireGuard 官方文档里，看着很吓人。逐个解释：

| 术语 | 白话 |
| --- | --- |
| RTNL | Routing Netlink。内核里管理网络接口的子系统 |
| link | 内核对一个网络接口的称呼。`ip link` 命令操作的就是它 |
| netlink | 内核和用户程序之间传消息的通道。比老式的 `ioctl` 灵活 |
| Generic Netlink | netlink 的一个通用分支。新协议都往这里放 |
| `ioctl(2)` | 一种老式的系统调用，靠来回传结构体交换参数 |
| `wg(8)` | `wg` 这个命令行工具。括号里的 8 是手册分类号，指系统管理命令 |

官方文档有一段话说：为了和 `ip` 这类工具集成，WireGuard 注册了一个虚拟接口；配置接口密钥时先试过 RTNL 消息，太受限；又试过自己实现 `ioctl`，不够干净；最后选了 Generic Netlink，于是有了独立的 `wg` 命令。

翻译成人话：

1. **WireGuard 把自己做成了一块普通网卡。** 所以 `ip link` 能看到它，`ip route` 能给它配路由。
2. 剩下那些是它**怎么和内核通信**的实现选型。

结论：这些是内核开发者的细节。普通使用者只需要知道两条命令：`wg`（看状态、配置）和 `wg-quick`（起停）。

### 问题 19：什么是网络命名空间？套接字和网卡为什么能分开？

| 术语 | 白话 |
| --- | --- |
| 网络命名空间 | 一套独立的网络视图。网卡、路由表、防火墙规则各有一份 |
| 容器 | 用命名空间隔离出来的一组进程 |

WireGuard 有个特性：它的虚拟接口可以在命名空间之间移动。

```text
普通做法：网卡和它的 UDP 套接字在同一个命名空间

WireGuard 允许：
  命名空间 A（容器里）：只有 wg0 这一块网卡
  命名空间 B（宿主机）：UDP 套接字在这儿，加密包从真实网卡发出
```

好处：容器里只需要一块 `wg0`。容器里所有流量自动加密。加密包从宿主机的真实网卡出去，容器不需要知道外面怎么走。

这是个「可以这么做」的特性，不是必须。如果你的容器直接跑在宿主机网络上，就不需要它。

### 问题 20：外层包也要查路由表，会不会打转？

会。内层包交给 `wg0` 时查一次路由表。外层包（UDP 加密封装）要发出去时又查一次。

两次查表可能互相干扰，形成循环。经典场景是 `AllowedIPs = 0.0.0.0/0` 的全局代理，外层包一看路由表，又该走 `wg0`，就死循环了。

内核用 **fwmark**（给包打个标记，让路由规则区别对待）或者命名空间来避免。配置里那个 `Table = off` 也是干这件事的。

## 第五部分：Kubernetes 的 NodePort

前面的知识在这里会合。

### 问题 21：NodePort 是怎么转发的？

Kubernetes 里给 Service 设 `type: NodePort`，集群会在 `30000-32767` 这个范围里分配一个端口。**每台节点**都在这个端口上监听。

真正干活的是 **kube-proxy**。它在每台节点上装 iptables 规则。规则链大致是：

```text
KUBE-SERVICES      总入口，从 nat PREROUTING 和 nat OUTPUT 进来
  KUBE-NODEPORTS   NodePort 专用，按 dport 匹配
    KUBE-EXT-xxx   外部流量
      KUBE-SVC-xxx 选一个 Pod
        KUBE-SEP-xxx 真正的 DNAT，改成 Pod 的 IP 和端口
```

回到问题 2。这些规则在 PREROUTING 阶段就把目的地址改掉了，所以一个发往节点自己的包，也能被转到别的节点上的 Pod。

### 问题 22：externalTrafficPolicy 的 Cluster 和 Local 有什么区别？

这个字段决定 kube-proxy 生成什么规则。我实测对比过：

| 端口 | 服务类型 | 策略 | 节点 A | 节点 B | 节点 C | 节点 D |
| --- | --- | --- | --- | --- | --- | --- |
| 30080 | 入口网关（Pod 在节点 A） | Local | 通 | 不通 | 不通 | 不通 |
| 31981 | 业务 Pod（Pod 在节点 B） | Cluster | 通 | 通 | 通 | 通 |

两个值的差别：

- **`Local`**：只有**本机有 Pod** 的节点才接受 NodePort。其它节点把包丢掉，而且不回 RST，所以客户端表现为超时，不是拒绝。好处是 Pod 能看到真实客户端 IP。
- **`Cluster`**：所有节点都接受。包到了没有 Pod 的节点，再转发一跳。跨节点时源地址会被改写，所以 Pod 看不到真实客户端 IP。

`Local` 策略的规则长这样，最后一行是关键：

```text
KUBE-EXT-xxx
  1. 源在集群内部网段        → KUBE-SVC   所有端点
  2. 源是本机地址            → 打标记做 MASQUERADE → KUBE-SVC
  3. 其它（真正的外部流量）  → KUBE-SVL   只含本机端点
```

`KUBE-SVL` 是 `Local` 专用的链。本机没有端点时它是空的，包就丢了。

这就是为什么「通了/不通」会随节点变化。排查 NodePort 问题时，先看这个字段。

## 第六部分：完整案例

### 问题 23：一条路从头到尾是怎么走的？

背景：把集群的 `30000-32767` 整个范围暴露到公网，不改 apiserver 的 NodePort 配置。

方案：一台公网 VPS 加一条 WireGuard，VPS 把整段 TCP 原端口转进隧道。

```text
公网客户端
  → 203.0.113.10:30000-32767
  → VPS 上 DNAT 到 10.99.0.2 的同号端口
  → WireGuard
  → 入口节点 10.10.1.10
  → kube-proxy
  → 本机 Pod，或经 Calico 到其它节点
```

地址分工：

| 位置 | 地址 | 作用 |
| --- | --- | --- |
| VPS 公网 | `203.0.113.10` | 用户入口 |
| VPS 隧道口 | `10.99.0.1/24` | 监听 UDP 51820 |
| 入口节点内网口 | `10.10.1.10` | 集群入口，Calico 节点地址 |
| 入口节点隧道口 | `10.99.0.2/24` | DNAT 的目标 |

两个细节：

**一、DNAT 目标是隧道地址 `10.99.0.2`，不是内网地址 `10.10.1.10`。** 因为只有 `10.99.0.2` 才会进隧道。

**二、隧道的两端地址是自选的。** `10.99.0.0/24` 跟云厂商和机房都无关，只在这条隧道里有效。

为什么这个方案能work：业务 Pod 的 Service 都是 `Cluster` 策略（问题 22）。所以 DNAT 只打到入口节点也没关系，Pod 在别的节点照样能转过去。

为什么不用现成的端口转发工具，以及那条路是怎么失败的，见问题 24 到 28。

### 问题 24：frp 的原理是什么？和 WireGuard 有什么不同？

两者最根本的区别一句话：**frp 搬的是「连接」，WireGuard 搬的是「包」。**

**frp 是反向代理。**

先看它要解决的前提：内网没有公网入口，但内网能主动往外拨号。frp 利用的就是这一点。

```text
1. frpc 从内网主动连到公网的 frps:7000
   这条叫控制连接，只有一条 TCP

2. frpc 通过这条连接告诉 frps：我要占用 30256 端口
   frps 于是在公网开一个 :30256 的监听

3. 外部用户连 frps:30256
   frps 通过控制连接通知 frpc「有人来了」

4. frpc 收到通知，再主动拨一条新 TCP 到 frps
   这条叫工作连接（默认多路复用时是已有 TCP 里的一个流，见问题 26）

5. frps 把「用户的连接」和「工作连接」的字节流对接
6. frpc 再拨一条 TCP 到内网目标，也对接起来
```

一个外部 SSH 会话，实际会产生**三条 TCP 连接**：

```text
客户端 ──TCP#1──> frps:30256
                    │ frps 把 #1 和 #2 对接
frpc   ──TCP#2──> frps:7000
                    │ frpc 把 #2 和 #3 对接
frpc   ──TCP#3──> 内网 Pod:22
```

TCP 在这里被**终结了两次**。用户的 TCP 头、序号、窗口都不会进入隧道。三段连接各自握手、各自重传。这不是问题 14 里那种「TCP 包装进 TCP」，见问题 25。

**WireGuard 是虚拟网卡。** 它不关心里面跑什么协议。

```text
1. 外部用户连 VPS:30256
2. VPS 上一条 DNAT 规则把目的地址改成 10.99.0.2
   查路由表，发现 10.99.0.2 走 wg0
3. 整个 IP 包加密，套一个 UDP 头，发出去
4. 对端收到，解密，把原始 IP 包放回内核
5. 内核继续按原来的方式处理
```

同一个 SSH 会话，只有**一条 TCP 连接**：

```text
客户端 ──TCP#1──────────────────────> 内网 Pod:22
          中间被切成 IP 包，加密后走 UDP
```

TCP 是端到端的，中间只是被包起来。

对照表：

| | frp | WireGuard |
| --- | --- | --- |
| 工作在层 | 应用层，操作「流」和「端口」 | 网络层，操作 IP 包 |
| 核心机制 | 反向代理，两条流对接 | 虚拟网卡，包加密 |
| 公网侧需要什么 | 每个端口一个 listener | 一个 UDP 端口加一条 DNAT 规则 |
| 暴露 2769 个端口 | 2769 个注册对象 | 1 条规则 |
| 配置粒度 | 每个端口一条 | 一个网段 |
| 一个会话几条 TCP | 3 段 | 1 条 |
| 是否终结 TCP | 是，终结两次 | 否 |
| 有无控制连接 | 有，全部代理挂在它上面 | 无 |
| 断线后 | 全部端口同时失效 | 下一个包自动重新握手 |
| 隧道对端口 | 必须逐个登记 | 完全不感知 |
| 隧道里装的是 | 重新包装过的字节流 | 完整的 IP 包 |
| 隧道承载协议 | 默认 TCP，可选 QUIC、KCP | 固定 UDP |

**为什么一个适合少量端口，一个适合整段。**

frp 里**端口是一个有名字、有状态的对象**。`ssh-30256` 这个名字、这个 listener、这条注册记录，都要占 frps 和 frpc 的资源，都要通过同一条控制连接维护。2768 个就是 2768 份状态，压在一条连接上。

WireGuard 对端口**完全没有概念**。它只认 IP 包。DNAT 规则是 `30000:32767` 一整段，转发 1 个端口和转发 2768 个端口，对隧道来说一模一样。

所以：只暴露 3 个端口，frp 很合适，配置直观，还能按端口做权限。要暴露一整段随机分配的端口，WireGuard 合适，因为隧道不关心端口。

### 问题 25：frp 是 TCP 里面包 TCP 吗？

严格说不是。frp 是应用层代理。它把用户那条 TCP 里的字节读出来，再写进隧道。它不会把 TCP 包整个封装进去。

**WireGuard：封装整个 IP 包。**

```text
用户的 TCP 包（含 IP 头、TCP 头）
  └─ 整个被加密，塞进 UDP 载荷
       └─ 送到对端，再原样还原
```

用户和内网服务之间只有一条 TCP 连接。握手、序号、重传都是它们两端自己完成的。隧道只是一根透明的网线。

**frp：在中间截断，变成三条独立的连接。**

```text
用户 ──TCP#1──> frps ══TCP#2（隧道）══> frpc ──TCP#3──> 本地服务
```

- TCP#1：用户和 frps 之间。frps 在这里完成三次握手，TCP 到此终止。
- TCP#2：frpc 和 frps 之间的隧道。开启多路复用时，是一条 TCP 里的多个流。
- TCP#3：frpc 和本地服务之间。frpc 自己新建。

frps 只做一件事：把 TCP#1 收到的字节流，包上 frp 自己的消息格式，写进 TCP#2。frpc 收到后拆出来，写进 TCP#3。反方向同理。

这意味着什么：

**没有典型的 TCP meltdown。** 那个问题出在把 TCP 包塞进 TCP，例如 OpenVPN 的 TCP 模式。内外两层重传机制互相放大。这才是问题 14 说的情况。frp 里没有「内层 TCP 包」，所以不会出现这种雪崩。

**仍有队头阻塞。** 开启多路复用后，所有用户的字节共用 TCP#2。它丢包重传时，里面所有流都得等。

**端到端语义被切断。** 用户的 TCP 握手成功，只说明 frps 接住了，不代表本地服务可达。本地服务连不上时，frps 才会关闭 TCP#1。用户先看到的是「连上了又断开」。

**frps 能看到每个连接的字节流。** 所以它才能做 HTTP 按域名转发、限速、统计流量。这些 WireGuard 做不到。

**用户看到的源 IP 变了。** 本地服务看到的连接来自 frpc，不是真实用户。需要靠 proxy protocol（在连接开头附带原始客户端地址）之类的方式传递原始 IP。WireGuard 加 DNAT 时，源 IP 可以保留（取决于是否做 SNAT，见问题 29）。

**UDP 怎么办。** frp 也能代理 UDP 端口。做法是把 UDP 数据报逐个包进隧道消息里，通过 TCP#2 传输。这种情况下才是真正的「UDP 内容走 TCP」，会带来延迟抖动。对实时性要求高的 UDP 业务，frp 效果一般。

隧道本身可以换传输协议：`transport.protocol` 支持 `tcp`（默认）、`kcp`、`quic`、`websocket`。选 `quic` 时，TCP#2 这一段就变成 UDP 承载，能缓解队头阻塞。frp 的「控制连接 + 代理注册」这套有状态机制没有变。

一句话对比：

| | WireGuard | frp |
| --- | --- | --- |
| 工作层次 | 网络层，转发 IP 包 | 应用层，转发字节流 |
| 隧道里装的是 | 完整的 IP 包 | 重新包装过的字节流 |
| 端到端 TCP 连接数 | 1 条（用户到服务） | 3 段 |
| 隧道承载协议 | UDP | 默认 TCP，可选 QUIC、KCP |

### 问题 26：frp 隧道是否多路复用有什么区别？

区别在于：用户的每次访问是新开一条 TCP，还是在已有的 TCP 里新开一个流。其他部分（控制连接、端口、配置的代理）都一样。

| | 开启多路复用（默认） | 关闭多路复用 |
| --- | --- | --- |
| 隧道由什么组成 | 1 条 TCP，里面分成多个流 | 1 条控制连接，加上每次访问一条工作连接 |
| 新访问的开销 | 发一个帧，开一个流，没有握手 | frpc 要新建一条 TCP 并握手，多一个往返 |
| 并发 1000 个访问时的隧道连接数 | 1 条 | 约 1000 条（加 1 条控制连接） |
| 隧道断开的影响 | 所有流同时中断 | 控制连接断了所有代理失效；已在传输的工作连接各自独立 |
| 丢包或网络抖动 | 所有流一起被拖慢（队头阻塞） | 只影响出问题的那条连接 |
| 资源占用 | 文件描述符、NAT 表项都很少 | 随并发线性增长 |

怎么选：绝大多数场景保持默认开启。尤其是 2000 个端口这种代理数量多、单个端口并发不高的情况，连接数少的好处很明显。隧道链路丢包明显、长连接互相影响时，可以考虑关闭。

两种模式下，控制连接都是单点。它断了，2769 个代理照样全部失效。关闭多路复用主要改善的是丢包时的相互影响，不能解决「连接被回收后 frpc 没重连」。那一类问题见问题 28。

### 问题 27：控制连接和工作连接都是 TCP 吗？端口是什么情况？

本质：控制连接和工作连接都是普通的 TCP 连接。连的是同一个端口（frps 的 `bindPort`，如 7000）。没有任何区别。区别只在连上之后发的第一条消息。

**控制连接传什么。** 它不传用户数据。它决定这个 frpc 现在是不是在线，以及它名下有哪些代理有效。按时间顺序：

1. 登录：frpc 启动后主动连到 frps 的 7000，发送登录消息。frps 回复登录成功。问题 28 日志里的 `client login info` 就是这一步。
2. 注册代理：frpc 把每个代理发给 frps，frps 开始监听对应的 `remotePort`。2769 个代理就是在这里注册的。
3. 心跳：之后定期互发 ping/pong。
4. 通知建工作连接：有用户访问时，frps 通过控制连接告诉 frpc「来了一个访问」。
5. 其他管理消息：代理关闭、配置变更等。

**怎么区分。** frpc 每建一条 TCP 连到 `frps:7000`，frps 都是读第一条消息来判断：

- 第一条是 Login：这是控制连接。
- 第一条是 NewWorkConn：这是工作连接。frps 把它交给正在等待的那个用户访问。

连接类型靠「第一句话」决定，不是靠端口，也不是靠 TCP 本身的任何特性。

**端口的情况。** 关闭多路复用时：

| 连接 | frpc 一侧（源） | frps 一侧（目标） |
| --- | --- | --- |
| 控制连接 | 临时端口，如 5544 | 7000 |
| 工作连接 1 | 临时端口，如 5545 | 7000 |
| 工作连接 2 | 临时端口，如 5546 | 7000 |

frps 一侧永远只有 7000 一个端口。所有连接都是它 accept 出来的。frpc 一侧每条连接由系统随机分配一个临时端口。四元组不同，所以多条连接共存互不冲突。

另外两个端口和隧道无关：用户连的是 frps 的 `remotePort`（如 10000）。frpc 连本地服务用的是 `localPort`。

**开启多路复用时。** 只有 1 条 TCP（frpc 临时端口 → frps:7000）。控制连接和工作连接不再各占一条 TCP，而是这条 TCP 里 yamux（一种把一条 TCP 切成多个逻辑流的协议）划分出的不同流：第一个流发 Login，当控制流用；之后每个用户访问开一个新流，发 NewWorkConn，当工作流用。从网络上看，端口和连接数都只有那一份。

一句话：**不管开不开多路复用，隧道方向的流量都只用 frps 的 7000 这一个端口。** 多路复用只改变「这些逻辑连接是各占一条 TCP，还是共用一条」。

**为什么控制连接断了影响这么大。** frps 把「这个 frpc 的所有代理」都挂在控制连接上。控制连接一断，frps 认为这个客户端下线了，就会立刻关掉它名下所有监听端口。这正好对应问题 28 日志里的现象：`client exit success` 之后，2769 个 listener 在同一秒内全部关闭。

反过来，只要控制连接还在，就算个别工作连接出问题，也只影响单次访问。

frpc 检测到控制连接断开后，正常会自动重连、重新登录、重新注册所有代理。问题 28 的日志里 frps 只收到一次登录，说明断开之后 frpc 没有发起新的登录。

### 问题 28：为什么之前用 frp 不行？

这个问题的答案有证据。frps 的日志在 VPS 上留了下来。

```text
16:04:01      frps 启动，监听 :7000
16:35:54.947  frpc 登录，来源 198.51.100.20:5544，版本 0.61.1，arm64
16:35:54.991  开始注册代理
16:35:55.034  注册完毕，共 2769 个，耗时不到 1 秒
              （30000-32767 共 2768 个，加 web 一个）
16:36:34.983  client exit success
              2769 个 listener 在同一秒内全部关闭
17:35:11      frps 被停
```

关键数字：**整个生命周期里，`client login info` 只出现 1 次，`client exit` 只出现 1 次。**

也就是说，从 16:36:35 到 17:35:11 这 59 分钟里，frpc 一次都没有重连。

从日志能确定四件事：

**一、VPS 侧没有报任何错。** 没有错误，没有告警，没有心跳超时，没有内存或句柄不足。2769 个代理全部注册成功。

**二、连接是从客户端那一侧干净关闭的。** `client exit success` 是 frps 收到正常 EOF 时的日志。不是被 frps 踢掉，也不是异常断开。

**三、Kubernetes 显示它是健康的。** 当时 Pod 是 Running，重启次数 0。所以编排系统认为一切正常，而实际上 2769 个端口全是死的。

**四、40 秒这个数字很可疑。** 登录后爆发式注册，然后空闲，40 秒后连接消失。但 frpc 那一侧的日志已经随 Pod 删除而丢失，所以**具体原因无法证实**。可能是链路上的空闲超时，也可能是中间设备重置。这一段只是推测。

不管那 40 秒的具体原因是什么，设计上有五个问题：

**一、一个连接承载全部。** 2769 个代理全部复用同一条控制连接。这条连接一断，2769 个端口同时失效。这正是发生的事。见问题 27。关闭多路复用也救不了这一条，见问题 26。

**二、静默失败。** 进程活着，Kubernetes 就报健康。所以监控看不出来。这种故障最难查。

**三、不自动恢复。** 登录一次，断了就再也没回来。

**四、资源开销大。** 2769 个监听套接字，每个还有自己的协程和缓冲区，都压在内存 1.7 GB 的 VPS 上。WireGuard 只需要 1 个 UDP 套接字和 1 条 iptables 规则。

**五、新端口要改配置。** 端口范围写死在 ConfigMap 里。新分配一个范围外的 NodePort，就得改配置再重启。

有一个细节值得注意：frpc 的出网地址 `198.51.100.20:5544`，和 WireGuard 的对端是同一个出口。**同样的链路，同样的中间设备。**

区别在传输方式。frp 用 TCP 长连接，靠 30 秒心跳保活，40 秒就断了。WireGuard 用 UDP，25 秒保活，此后一直稳定。

TCP 长连接在 NAT 后面本来就脆弱：NAT 会记录每条连接的状态，空闲久了就回收。UDP 没有连接状态可回收，加个定期保活就能一直通。这是换成隧道之后顺带解决的问题。

### 问题 29：为什么回程必须做 MASQUERADE？

VPS 在隧道口上做了 **MASQUERADE**。这是自动改源地址的 SNAT。

它把内层包的源地址改成 `10.99.0.1`。

为什么必须这样做：入口节点不知道公网客户端的地址，也没有回公网的路由。如果源地址保留成客户端地址，节点会把回包丢给内网网关，客户端永远收不到。

代价：入口节点看不到真实客户端 IP。

一条真实的 conntrack 记录：

```text
正向  src=10.99.0.1    dst=10.99.0.2  sport=61433  dport=32763
      DNAT 后实际送到 10.244.2.5:22
回向  src=10.244.2.5   dst=10.244.1.0  sport=22  dport=5914
```

**conntrack** 是连接跟踪，内核记录每条连接，回包时自动反向还原地址。

`10.244.1.0` 是入口节点上 Calico 隧道网卡的地址。回包从 Pod 所在节点经 Calico 隧道回到入口节点，再反向还原成 `10.99.0.2`，进隧道，最后由 VPS 还原成客户端地址。

## 第七部分：两个真实故障

这部分是我做完上面的改造后遇到的坑。两个坑都不是 WireGuard 本身的问题，但都值得记下来。

### 故障一：DNS 超时，网页一直转圈

**现象**：内网访问集群里的网页，一直转圈，最后超时。

**排查过程**：

```text
1. NodePort 的 TCP 能连上，但 HTTP 不回           → 不是路由问题
2. 从入口节点本机访问也超时                        → 不是防火墙问题
3. 从入口网关 Pod 内部访问 127.0.0.1:80 也超时     → 问题在 Pod 内
4. 同一个 Pod 的健康端口 10254 返回 ok             → 进程还活着
5. 日志：failed to receive reply from UDP server 10.96.0.10:53: timeout
```

**原因**：集群 DNS 服务的配置是 `forward . /etc/resolv.conf`，而节点的 `/etc/resolv.conf` 把一个公网 DNS 放在第一位。这个 DNS 从 Pod 网络访问不到。

每个外部域名查询都会占住一个工作线程直到超时。线程被占满之后，集群内部的域名也答不了。入口网关查不到上游服务名，就返回 503 或者挂住。

**顺序很重要**：先出现的是 DNS 上游超时，然后才连累到内部域名。看到「内部域名解析失败」时，不要只盯着内部域名。

**恢复**：重启 DNS 服务和入口网关，清掉卡住的查询。然后改 DNS 服务的 `forward` 指向 Pod 能访问的地址。

### 故障二：Calico 把节点地址认成了隧道地址

**现象**：入口节点上的 `calico-node` 变成 NotReady，报 `BGP not established`。

**背景**：Calico 是容器网络方案。它用 **BGP** 协议在各节点之间交换路由。`BGP` 是互联网上用的路由协议，Calico 借它来让节点互相知道对方的 Pod 网段在哪。

**原因**：Calico 会自动挑选节点地址。隧道起来了以后，它选中了隧道口，把入口节点认成了 `10.99.0.2`。另外三台节点仍然用 `10.10.1.10` 做 BGP 对端，会话建不起来。

**修复**：固定跳过隧道口，并显式指定节点地址。

```bash
kubectl -n kube-system set env ds/calico-node \
  IP_AUTODETECTION_METHOD=skip-interface=wg0
kubectl annotate node <入口节点名> \
  projectcalico.org/IPv4Address=10.10.1.10/16 --overwrite
```

**教训**：这台机器上以后新增**任何**虚拟接口（VPN、隧道、网桥），都要想到 Calico 可能把它误认成节点地址。

这类工具的自动探测逻辑，在接口变多之后很容易选错。显式指定比依赖自动探测可靠。
