## 第一部分：地址空间的形状

### 问题 1：一个进程的虚拟地址空间有多大？

取决于页表的级数。

| 模式 | 用户空间 | 地址范围 |
|---|---|---|
| **x86-64 四级页表**（主流） | **128 TB** | `0x0000_0000_0000` – `0x0000_7FFF_FFFF_FFFF` |
| x86-64 五级页表（LA57） | 64 PB | 低半部分 |
| 32 位（3G/1G 划分） | 3 GB | `0x0000_0000` – `0xBFFF_FFFF` |
| 32 位开启 PAE | 仍是 4 GB | 物理能到 64 GB，虚拟不变 |

关键词是**虚拟**。这个数字和物理内存没有任何关系。

### 问题 2：128 TB 这个数是怎么来的？

四级页表下，虚拟地址的有效位是 48 位，其中低半部分归用户，高半部分归内核：

```text
47 位索引空间的一半 = 2^47 字节 = 128 TB
```

高半的另外 128 TB 是内核的。中间那一大段是**非规范地址**（non-canonical）——CPU 规定地址的第 63 位到第 48 位必须是第 47 位的符号扩展，不满足的地址直接被拒绝，连异常都不会好好报。

五级页表把有效位提到 57 位，于是用户空间变成 2^56 = 64 PB。

实际可用略小于 128 TB，因为底部留了 `mmap_min_addr`（默认 64 KB，防止空指针被映射），栈顶要留 vsyscall 和 guard gap，栈和 mmap 区之间还要留安全距离。

### 问题 3：地址空间里各个区域是怎么排布的？

从高到低大致是这样（以 Linux x86-64 为例）：

```text
高地址 0x7fff_ffff_ffff
        ┌───────────────────────────┐
        │  栈（向下增长）            │  ← 栈顶随机
  0x7f… ├───────────────────────────┤
        │  mmap 区（向下增长）        │  ← 起点随机
        │  ├─ 动态库 .so            │
        │  ├─ mmap() 的文件映射      │
        │  └─ 大块 malloc            │
        ├───────────────────────────┤
        │      （中间大片空白）       │
        ├───────────────────────────┤
        │  堆（向上增长）            │  ← 紧接主程序
        ├───────────────────────────┤
        │  .bss / .data / .text     │  主程序映像
        │                           │  ← 基址随机（PIE 时）
  0x55… └───────────────────────────┘
低地址 0x0000_0000_0000（不可映射）
```

三条容易忽略的关系：

1. **动态库住在 mmap 区里。** `.so` 不是独立的一块，就是动态链接器通过 `mmap(NULL, …)` 从 mmap 区分到的一段。
2. **堆紧贴主程序。** `brk` 从主程序末尾往上长。所以主程序不随机时，堆也跟着固定。
3. **各区之间留着空隙。** 栈和 mmap 区之间要留出栈的最大可能大小，防止栈长下来撞上去；堆和 mmap 区之间留大片空白，让两者相向生长。

### 问题 4：程序运行时只有三块内存区吗？

不是。「代码数据 / 堆 / 栈」只是最显眼的概括，实际一个进程有几十个区域。

我写了个最小程序（一个线程 + 一次 1 MB `malloc` + 一次 64 KB `mmap`），实测：

```console
VMA 条数: 25

  5  /tmp/mm                      ← 主程序自己的 5 段
  5  /usr/lib/.../libc.so.6       ← 每个库都占多段
  5  /usr/lib/.../ld-linux.so.2   ← 动态链接器自己
  5  [匿名]                        ← 线程栈、malloc 的 1MB、mmap 的 64KB
  1  [stack]                       ← 只有主线程的栈有这个名字
  1  [heap]
  1  [vdso]
  1  [vvar]
  1  [vvar_vclock]
```

几个观察：

- **每个二进制、每个库都占 5 段**，不是 1 段。因为权限不同必须分开：ELF 头、代码（可执行）、只读数据、重定位页、可写数据。
- **线程栈是匿名的**，没有 `[stack]` 名字，所以 25 个里只有一个 `[stack]`。
- `[vdso]`、`[vvar]`、`[vvar_vclock]` 是内核塞进来的小映射，后面问题 23 会讲。
- 地址空间是一堆区域的集合，中间有大量空洞。所以一个进程的地址空间可能横跨几百 TB，却只用了 20 MB 物理内存。

## 第二部分：地址怎么被翻译

### 问题 5：MMU 是什么？

**MMU = Memory Management Unit，内存管理单元**，CPU 里负责地址翻译和权限检查的硬件。每次取指、每次读写内存都要经过它。

```text
  程序用的虚拟地址
        │
        ▼
  ┌─────────────────────────────────────┐
  │  MMU（在 CPU 内，每个核一份）        │
  │   1. 查 TLB（翻译缓存），命中就出结果 │
  │   2. 没命中 → 走页表逐级查            │
  │   3. 检查权限位（可读/可写/可执行/用户）│
  │   4. 违规 → 触发 #PF 缺页异常         │
  └─────────────────────────────────────┘
        │
        ▼
   物理地址 → 内存总线 → DRAM
```

三个部件：

| 部件 | 作用 |
|---|---|
| **页表** | 操作系统维护的多级映射表，记录「哪个虚拟页对应哪个物理页 + 什么权限」 |
| **TLB**（Translation Lookaside Buffer，翻译后备缓冲） | MMU 内部的缓存，存最近的翻译结果。命中约 1 个周期，未命中要查 4 级页表 |
| **页表遍历器**（page-table walker） | TLB 未命中时，硬件自动逐级读页表完成翻译 |

早期 MMU 是独立芯片（如 Motorola 68020 要配 68851），80386 把它集成进了 CPU，同时引入分页。

### 问题 6：页表是一张表吗？PGD 是什么？

页表是**一棵多级树**。x86-64 四级页表，每级都是一张 4 KB 的页，装 512 个 8 字节表项：

```text
CR3 ──▶ PGD (4 KB, 512 项)
          └─每项──▶ PUD (4 KB, 512 项)
                      └─每项──▶ PMD (4 KB, 512 项)
                                  └─每项──▶ PTE (4 KB, 512 项)
                                              └─每项──▶ 物理页 4 KB + 权限位
```

虚拟地址被切成五段，每层用 9 位索引：

```text
 47    39 38    30 29    21 20    12 11     0
┌────────┬────────┬────────┬────────┬────────┐
│PGD 索引│PUD 索引│PMD 索引│PTE 索引│ 页内偏移│
│  9 bit │  9 bit │  9 bit │  9 bit │ 12 bit │
└────────┴────────┴────────┴────────┴────────┘
```

**PGD = Page Global Directory，页全局目录**，就是最顶上那一层。`CR3` 寄存器存的是当前正在用的那个 PGD 的物理地址。

读 Intel 手册和读 Linux 源码要对得上名字：

| 层 | Intel 官方名 | Linux 里的名字 |
|---|---|---|
| 第 4 级（顶） | PML4 | **PGD** |
| 第 3 级 | PDPT | PUD |
| 第 2 级 | PD | PMD |
| 第 1 级 | PT | PTE |

`mm->pgd` 是这个进程的顶层页表；`swapper_pg_dir` 是内核母版的顶层页表（`init_mm.pgd`）。

### 问题 7：一个进程有几个页表？线程呢？`fork` 呢？

| 单位 | 有几棵树 |
|---|---|
| 一个**进程** | 1 个地址空间（`mm_struct`）→ **1 棵页表树** |
| 同一进程的多个**线程** | 共享同一个 `mm_struct` → **共用同一棵** |
| `fork` 出来的子进程 | **各自一棵**，内容复制一份（写时复制） |

两处「共享」的例外：

- **内核空间的映射**在每个进程的页表里都有（高半部分），所有进程共用同一批内核页表页
- **共享库的物理页**大家共用，但页表项各自独立——指向同一页，记录各有一份

页表本身也是内存。一个普通进程的页表通常占几百 KB，大内存程序能到几十 MB。页表页不会被换出到磁盘。

### 问题 8：分段是什么？IA-32 为什么要分段？

要分两个时代说，因为**最初的动机和保护完全无关**。

**第一代（8086，1978）：纯粹为了扩容。**

8086 的寄存器是 16 位，地址总线是 20 位（1 MB）。16 位最多表达 65536，够不到 1 MB。解决办法是把地址拆成两半：

```text
物理地址 = 段寄存器 × 16 + 16 位偏移
```

段寄存器左移 4 位当基址，再和偏移相加。两个 16 位拼出 20 位。段基址最大 `0xFFFF0`，偏移最大 `0xFFFF`，结果是 `0x10FFEF`，比 1 MB 多出 64 KB 减 16 字节。

所以第一代分段的本质是**在 16 位寄存器宽度限制下的扩容妥协**，与安全无关。

**第二代（80286）：改造成保护单位。**

80286 的保护模式里，段基址不再靠左移，而是**查表**：

```text
逻辑地址 = 段选择子(16位) + 偏移
              │
              ▼
         查 GDT / LDT 里的段描述符
              │
              ├─ 基址   → 线性地址的起点
              ├─ 限长   → 越界就 #GP（一般保护异常）
              ├─ 类型   → 可读/可写/可执行
              └─ DPL    → 特权级（ring 0–3）
```

一个机制同时给了三件事：边界检查、特权隔离（`DPL` 与 `CPL` 比较，`CPL` 存在 `CS` 选择子的低 2 位）、权限控制（代码段可标记「只执行不可写」）。

### 问题 9：GDT / LDT 是什么？HMA 是什么？

**GDT = Global Descriptor Table，全局描述符表；LDT = Local Descriptor Table，局部描述符表。** 都是内存里的段描述符数组，每个元素 8 字节：

```text
┌──────────┬───────────┬──────┬─────┬───┬─────────┐
│  基址    │   限长     │ 类型 │ DPL │ P │  其他   │
│ 32 bit   │  20 bit    │      │     │   │         │
└──────────┴───────────┴──────┴─────┴───┴─────────┘
```

两张表的区别只在作用范围：

| | GDT | LDT |
|---|---|---|
| 数量 | 每颗 CPU 一份，全系统共享 | 每个任务一份，可选 |
| 放什么 | 内核/用户代码段、数据段、TSS、**指向各 LDT 的描述符** | 该进程私有的段 |
| 上限 | 8192 项 | 8192 项 |

段寄存器里存的不是地址，而是 16 位的**选择子**：

```text
 15                   3  2  1  0
┌──────────────────────┬──┬─────┐
│      index（13 位）   │TI│ RPL │
└──────────────────────┴──┴─────┘
```

13 位索引 → 每张表 8192 项，两张共 16384 项；GDT 第 0 项必须是**空描述符**（加载即异常，用来抓「段寄存器没初始化」），扣掉剩 **16383**——这就是「一个程序最多用 16383 个段」的来源。

现代操作系统基本不用 LDT，但保留了接口（Linux 的 `modify_ldt`，供 Wine 跑 16 位程序）。

**HMA**（High Memory Area，高端内存区）是分段的副产品。8086 的段:偏移最大能算出 `0x10FFEF`，但地址总线只有 20 根，第 21 位被丢掉，回绕到 `0x0FFEF`。80286 有 24 根地址线，回绕消失了，可有些老软件**依赖**这个回绕，于是 IBM PC/AT 加了一根叫 **A20 gate** 的硬件开关，关着时强制第 21 位为 0，模拟 8086 行为。

```text
0x00000 ┐
        │ 常规内存 640 KB
0x9FFFF ┘
0xA0000 ┐
        │ 上位内存 384 KB（显存 + BIOS ROM）
0xFFFFF ┘
0x100000 ┐
         │ HMA: 65520 字节（64 KB 减 16 字节）
0x10FFEF ┘
```

它是实模式下唯一能用上 1 MB 以上内存的一块，所以 `DOS=HIGH` 和 Windows 3.x 都往这里装。今天这套概念已经死了，64 位系统不存在 1 MB 边界。

### 问题 10：分段和分页是什么关系？

x86 的地址翻译路径是串联的：

```text
逻辑地址 ──[分段]──> 线性地址 ──[分页]──> 物理地址
```

分段在**必经之路**上，无法关闭——平坦模型只是把段基址设成 0、限长设成 4 GB，让这一步什么都不做。分页可以关：`CR0.PG = 0` 就退回纯分段。

这就是讲义里「保护模式下分段必须、分页可选」那句话的由来。

### 问题 11：现代系统为什么弃用分段，却没删掉？

80386 有 32 位寄存器后，段「扩容」的原始理由消失了，剩下的是纯粹代价：

- **外部碎片**：段是变长的，反复申请释放后内存被切碎，且没法像分页那样统一回收
- **段必须整体换入换出**：段大时页面调度失去意义
- **编程模型痛苦**：出现远指针、`段:偏移` 两段式指针，指针大小和算术都变复杂，编译器难写
- **共享和增长困难**：段要长大时可能没有连续空间
- **每个进程一套 LDT**，管理开销大

所以 1990 年代所有主流操作系统（Linux、Windows NT、Solaris）都选**平坦模型 + 分页**：段全部设成基址 0、限长 4 GB，只用分页做隔离。

**但不能删。** x86 的首要约束是向后兼容。于是段机制变成一条无害的直通路径，一代代保留至今。

今天只剩两个活口：

1. **FS / GS 段寄存器**：用作线程局部存储（TLS，Thread-Local Storage）的基址。x86-64 Linux 上，栈保护用的 canary 就是从 `FS:0x28` 读的。64 位模式下 `FS`/`GS` 的基址不再从描述符读，而是从 MSR 寄存器（`IA32_FS_BASE` / `IA32_GS_BASE`）读。
2. **`CS` 里的 `CPL`**：用户态/内核态的判定依据仍然是它。

这里有个代价值得记：段机制的保护其实比今天更严——代码段可以标记成不可写，相当于 20 年前就有的「禁止执行可写内存」。操作系统弃用分段后这部分能力丢了，一直到 2004 年 AMD 推出 NX 位（Intel 叫 XD bit）才靠分页补回来。中间那十年，缓冲区溢出可以随便在栈上执行代码。

## 第三部分：地址背后放着什么

### 问题 12：VMA 是什么？和页表项是什么关系？

**VMA = Virtual Memory Area**，内核里的 `struct vm_area_struct`，描述虚拟地址空间里**一段连续、属性相同**的区间。

| 字段 | 意思 |
|---|---|
| `vm_start` / `vm_end` | 这段地址从哪到哪 |
| `vm_flags` | 权限：可读 / 可写 / 可执行 / 共享 / 私有 |
| `vm_file` + `vm_pgoff` | 背后是哪个文件的哪一段（匿名则为空） |
| `vm_ops` | 缺页时调用哪个函数 |

一个 `mmap()` = 建立一个 VMA；`munmap()` = 删掉或拆分。这些 VMA 按地址排在树里（Linux 6.1 之前是红黑树，之后是 maple tree），查找 O(log n)。数量有上限 `/proc/sys/vm/max_map_count`（默认 65530）。

**最关键的一句：VMA 是「意图」，页表项是「事实」。**

```text
访问某个地址
   │
   ├─ 这地址在一个 VMA 里吗？
   │     不在 → SIGSEGV（段错误）
   │
   └─ 在 → 但页表项填了吗？
         没填 → 缺页中断 → 内核查这个 VMA 的权限和文件 → 现在填
         填了 → 直接访问
```

所以「段错误」的真正含义是**访问了没有 VMA 的地址**；而「缺页」是**有 VMA 但页表还没建**——后者是正常流程，前者才是 bug。

### 问题 13：页缓存是什么？

**页缓存（page cache）是 Linux 内核用来缓存磁盘文件内容的那部分物理内存**，以页（4 KB）为单位，按「哪个文件的第几页」索引。

```text
     用户程序            read()/write()  或者  mmap 的映射区
        │                      │                   │
        ▼                      ▼                   ▼
 ┌──────────────────────────────────────────────────────┐
 │  页缓存（内核内存，存的是文件页的副本）                │
 │  同一份数据，read() 会拷一份给用户；mmap 直接把页表     │
 │  指过来，不拷                                         │
 └──────────────────────────────────────────────────────┘
        │  miss 时读入 / 脏页回写
        ▼
     块设备层 ──▶ 磁盘
```

三个关键性质：

**① `write()` 返回 ≠ 数据已落盘。** `write()` 写的是页缓存，该页被标记为**脏页**，由内核回写线程过几秒批量刷盘。好处是小的写被合并、随机写被重排；风险是掉电丢数据。要保证落盘必须 `fsync()`。

**② 干净页随时可以丢。** 内存紧张时，干净页（和磁盘一致）直接扔掉，脏页必须先写回。所以页缓存**不算「被占用的内存」**——这就是 `free -h` 要把 `buff/cache` 单列、`available` 远大于 `free` 的原因。

**③ 全局共享。** 页缓存不属于任何进程。几十个进程映射同一个 `libc.so`，物理内存里只有一份。

三个常见误解：页缓存不是 CPU 缓存（它是 DRAM 里缓存**磁盘**）；不是内核预留的固定区域（它动态占用所有空闲内存）；`free` 很小不一定是问题，要看 `available`。

### 问题 14：页缓存和页表是什么关系？分别谁管？

| | 页缓存 | 页表 |
|---|---|---|
| 存的是 | **数据内容** | **翻译关系** |
| 索引方式 | 按 `(哪个文件, 第几页)` | 按 `虚拟地址` |
| 归属 | 文件（`inode`），全局共享 | 进程（`mm_struct`），每进程一份 |
| 核心结构 | `address_space`（挂在 `inode->i_mapping`），内部用 xarray 索引 | `mm_struct->pgd` → 四级页表页 |
| 能否丢弃 | 干净页随时可丢；脏页先回写 | 不能丢，只能随进程退出或 `munmap` |
| 回收者 | `kswapd` / LRU 链表 | 进程退出、`munmap` |

两者是**独立**的子系统，谁也不归谁管。**页缓存里没有虚拟地址，页表里没有文件偏移**——两条独立的索引，只在「物理页」这个对象上交汇：

```text
        文件第 0 页  第 1 页  第 2 页        ← 页缓存的索引
             │         │        │
             ▼         ▼        ▼
        物理帧 #7   #9      #12
             ▲         ▲        ▲
             │         │        │
   虚拟地址 0x7f00 ─────┘        │            ← 页表的索引
   虚拟地址 0x7f01 ──────────────┘
```

唯一需要「知道对方」的场合是**回收**：回收一页之前，必须把所有映射了它的页表项清掉，否则进程会访问到已被挪作他用的内存。这叫**反向映射**（reverse mapping）：

- `address_space->i_mmap` 存着「哪些 VMA 映射了这个文件的这段」
- `struct page` 上的 `_refcount`（引用计数）、`_mapcount`（多少个页表项映射了它）、`mapping`（属于哪个 `address_space`）三个字段把两边串起来

可以实测：

```console
$ grep -E 'Cached|PageTables' /proc/meminfo
Cached:           686772 kB    ← 页缓存
PageTables:        29748 kB    ← 所有进程的页表加起来
```

两列分别对应两个子系统。灌一个大文件进页缓存，`Cached` 涨而 `PageTables` 不变；起一个开很多线程的程序，`PageTables` 涨而 `Cached` 不变。

### 问题 15：匿名页是什么？和文件页差在哪？

**匿名页（anonymous page）是没有后备文件的物理页。** 页表项指向它，但磁盘上没有对应的副本。

| | 文件页 | 匿名页 |
|---|---|---|
| 背后是什么 | 磁盘上的一个文件 | 什么都没有 |
| 内核怎么认它 | `page->mapping` 指向 `address_space` | `page->mapping` 指向 `anon_vma`，**最低位标记为 1** 用于区分 |
| 有没有「名字」 | 有：`(哪个文件, 第几页)` | 没有名字，只记录「谁映射了它」 |
| 内容丢了能找回吗 | 能，从磁盘重读 | **不能**，只能 swap |
| 典型例子 | 代码段、`.rodata`、`mmap` 的文件、页缓存 | 栈、堆、`malloc`、`MAP_ANONYMOUS`、`fork` 后 COW 出来的副本、线程栈 |

「匿名」就是字面意思：它在文件系统里没有名字。文件页有身份，匿名页只有归属关系。

有个半匿名的特例：**`shmem` / `tmpfs`**。它挂在文件系统上有 `address_space`，但那块「磁盘」其实在内存里（或 swap 里），所以计入 `Shmem` 而不计入 `Cached`。

实测（一个 `mmap` 了 1 MB 匿名区并写满的进程）：

```console
Anonymous:   1024 kB       ← 那一块 1 MB 全是匿名页
RssAnon:     1120 kB
RssFile:     1580 kB       ← 二进制和 libc 的代码/只读数据是文件页
```

全系统：

```console
AnonPages:   3073232 kB    ← 3.07 GB 匿名页
Cached:       686772 kB    ← 0.69 GB 文件页（页缓存）
Shmem:         33132 kB
```

### 问题 16：为什么匿名页不能像文件页那样直接丢弃？

因为丢掉了就真没了。

```
内存不够时
  ├─ 文件页（干净）  → 直接丢弃，零成本，下次访问再从磁盘读
  ├─ 文件页（脏）    → 先写回，再丢
  └─ 匿名页          → 不能丢！只能写进 swap
                        ↓
                    没有 swap 或 swap 满了
                        ↓
                     OOM Killer
```

所以内核**优先回收文件页**，匿名页在内存里待得更久。这也解释了为什么内存紧张时 `Cached` 会被压得很低而 `AnonPages` 居高不下。

另一处区别在 `fork`：父子进程共享的栈、堆都是匿名页，写时才复制（写时复制，COW）；代码段是文件页，本来就只读，直接共享。

## 第四部分：从一个 `mmap` 看完整流程

### 问题 17：`mmap` 的「零拷贝」省掉的是哪一次拷贝？

对比传统 `read()`：

```text
传统 read()：
  磁盘 ──[DMA]──▶ 内核页缓存 ──[CPU 拷贝]──▶ 用户缓冲区
                        ①                    ②  ← 这次没了

mmap 后访问内存：
  磁盘 ──[DMA]──▶ 内核页缓存
                        ▲
                        └── 页表直接指过来 ──▶ 用户的虚拟地址
                        ①
```

`read()` 要拷贝两次：磁盘到页缓存（DMA 干，不占 CPU），再从页缓存复制到你的 `buf`（**CPU 干，占带宽**）。

`mmap` 后第二次拷贝消失了：用户指针直接指向页缓存那一页。所以叫**零拷贝**。

严格讲不是「零次拷贝」——磁盘到内存那次 DMA 省不掉。**省掉的是「内核空间 → 用户空间」那次 CPU 拷贝。**

除了省拷贝，还有三个好处：省内存（页缓存和映射共用同一份物理页）、按需调页（10 GB 文件只读 1 页就只装 1 页）、多进程共享（`MAP_SHARED` 映射同一文件，看到的是同一份物理页）。

代价和坑：缺页开销（文件小、只顺序读一遍时 `mmap` 可能比 `read()` 慢）、`SIGBUS`（访问超出文件长度的页）、一致性（`MAP_SHARED` 立即可见，`MAP_PRIVATE` 是 COW）、不能自动回收地址空间。

`mmap` 还是 attack surface 交汇点：`PROT_EXEC` + `MAP_ANONYMOUS` 是 shellcode 的标准落脚点（所以有 W^X 和 NX 位）；`mmap_min_addr` 专门防「把 NULL 附近映射成可控内存」；`MAP_FIXED` 可以强行覆盖已有映射。

### 问题 18：`mmap` 之后会立刻读文件吗？

不会。`mmap` 只做登记，数据始终只有一份，躺在页缓存里。

```text
第 0 步：mmap() 返回
        · 内核只创建一个 VMA，记录「这段地址对应哪个文件的哪一段」
        · 不读磁盘，不建页表项，不占物理内存
        · 占的是虚拟地址空间（几 GB 也没关系）

第 1 步：程序第一次访问 p[100]
        · CPU 查页表 → 这一页没有有效页表项 → 触发缺页异常
        · 内核查 VMA：「这是文件 X 的第 0 页」

第 2 步：内核建立连接
        · 页缓存里有没有这一页？
           有 → 直接把页表项指过去        （minor fault，次缺页，不读盘）
           没有 → 从磁盘读进页缓存，再指过去（major fault，主缺页，真 I/O）
```

三个容易搞错的地方：

1. **粒度是页，不是整块。** 访问 `p[100]` 只装入包含第 100 字节的那一页（4 KB），其余部分仍然是空的。
2. **不一定是「搬到那块区域」，很多时候连磁盘都不读。** 页已在页缓存里时，缺页只是填一个页表项。这就是 minor fault 和 major fault 的区别，能用 `/proc/<pid>/stat` 里的 `minflt` / `majflt` 观察。
3. **内核会预读。** 缺页一次，通常顺手把后面若干页一起读进来，所以实际磁盘 I/O 粒度大于 4 KB。

写的时候路径不同：`MAP_SHARED` 直接改页缓存那一页，标记为脏页，由内核回写；`MAP_PRIVATE` 触发 COW，复制一份新页，改动永不落盘。

唯一的例外是 `MAP_POPULATE` 标志——它会**马上**把页表全填好（相当于同步预读整个映射区），所以那时确实是「立刻读」。

可以自己验证：`mmap` 一个 1 GB 文件后立刻看 `/proc/<pid>/smaps` 的 `Rss`，接近 0；然后每隔 4 KB 访问一次，`Rss` 会一页一页涨上去。

### 问题 19：一个物理页在系统里有几个「名字」？

三个。

```text
                物理内存（DRAM）
                       │
    ┌──────────────────┼──────────────────┐
    │                  │                  │
    ▼                  ▼                  ▼
直接映射区          vmemmap            vmalloc 区
(线性地址=物理+偏移)  (每页一个           (虚拟连续,物理跳跃)
 用于读写数据        struct page)        用于模块/ioremap
    ▲                  ▲
    │                  └─ 元数据：描述每个物理页
    │
    └──── 用户进程页表 ────▶ 同一个物理页
             (每进程不同，随机)
```

1. **内核线性地址**：`物理地址 + page_offset_base`（固定偏移），内核用它读写内容
2. **`struct page`**：位于 vmemmap 区，记录引用计数、`_mapcount`、所属 `address_space`
3. **用户虚拟地址**：位于某个进程的地址空间，随机、每进程不同

`struct page` 是内核为每个物理页帧准备的描述符，64 字节左右：

```c
struct page {
    unsigned long flags;            /* 脏页？在 LRU 上？slab？ */
    atomic_t _refcount;             /* 有多少人在用 */
    atomic_t _mapcount;             /* 多少个页表项映射了它 */
    struct address_space *mapping;  /* 属于哪个文件 */
    pgoff_t index;                  /* 在文件里是第几页 */
    struct list_head lru;           /* 挂在 LRU 的哪个位置 */
    ...
};
```

数量很惊人。24 GB 内存 ÷ 4 KB = 630 万页，× 64 字节 ≈ 400 MB。**这 400 MB 全是登记信息，一个字节的用户数据都没有。** 它整体放在 vmemmap 区，因为要能按下标 O(1) 定位：

```text
某物理页的描述符地址 = vmemmap_base + 页帧号 × sizeof(struct page)
```

「对用户没有意义」有三层意思：它是账本不是内容；布局是内核私有 ABI（字段随编译选项变化）；地址在 vmemmap 区，用户态访问不到。用户想知道内存情况，走的是内核翻译好的接口：`/proc/meminfo`、`/proc/<pid>/smaps`、`/proc/<pid>/status`。

## 第五部分：内核自己的内存视图

### 问题 20：直接映射区是什么？为什么需要它？

内核把**全部物理内存**按固定偏移整体映射到一段虚拟地址上：

```text
内核线性地址 = 物理地址 + page_offset_base
```

`page_offset_base` 是启动时确定的常数（x86-64 上默认 `0xffff888000000000`）。给定任何物理地址，一条加法就能算出访问它的虚拟地址。

为什么必须有它，而不是全部用 `vmalloc`：

| | 直接映射区 | vmalloc 区 |
|---|---|---|
| 地址怎么算 | 物理地址 + 常量，一条 `add` | 查页表，逐页翻译 |
| 页大小 | 1 GB / 2 MB 大页 | 默认 4 KB |
| 分配开销 | 极低（只是标记某页被占用） | 每次都要改内核页表 + 刷 TLB |
| 是否要求物理连续 | 是（物理连续 → 虚拟连续） | 否 |

内核绝大部分内存（slab、页缓存、页表页、内核栈）都放在直接映射区，因为它们是热路径。`vmalloc` 只留给「必须虚拟连续但物理拿不到连续页」的场景：内核模块、`ioremap` 映射设备寄存器、大块 `vmalloc`。

32 位时代这里有个历史包袱。用户/内核按 3 GB / 1 GB 划分，直接映射区只有约 768 MB，物理内存超过 768 MB 的部分没法直接映射，只能临时借地址映射一下、用完就撤——这就是 `kmap()` / `kmap_atomic()` 和高低端内存（highmem）概念的来源，也是 32 位内核里一大堆 bug 的源头。64 位把直接映射区做到 64 TB，物理内存永远装得下，这个概念整个消失了。

### 问题 21：内核地址空间还有哪些区？

x86-64 四级页表下大致这样切分：

| 区域 | 起始地址 | 大小 | 干什么用 |
|---|---|---|---|
| 用户空间 | `0x0000_0000_0000` | 128 TB | 每个进程各自的页表 |
| **直接映射区** | `0xffff_8880_0000_0000` | 64 TB | 全部物理内存的线性映射 |
| **vmalloc / ioremap** | `0xffff_c900_0000_0000` | 32.5 TB | 虚拟连续、物理可不连续 |
| **vmemmap** | `0xffff_ea00_0000_0000` | 1 TB | `struct page` 数组 |
| cpu_entry_area | `0xffff_fe00_0000_0000` | 2 TB | 每 CPU 的入口栈、TSS、GDT |
| **内核映像** | `0xffff_ffff_8000_0000` | 512 MB | 内核自己的 `.text` / `.data` |
| **模块区** | `0xffff_ffff_c000_0000` | 1.5 GB | 内核模块（新版本并入 vmalloc 区） |
| KASAN 影子 | `0xffff_ff00_0000_0000` | ~16 MB | 内核内存越界检测 |
| vsyscall | `0xffff_ffff_ff60_0000` | 4 KB | 遗留系统调用入口 |

区域之间刻意留了大片**空洞（guard hole）**，越界访问会直接撞进未映射区，立刻崩溃而不是悄悄改坏别的东西。

具体数值随内核版本和配置变化。开了 `CONFIG_RANDOMIZE_MEMORY` 后，`page_offset_base`、`vmalloc_base`、`vmemmap_base` 都是**运行期变量**，每次启动随机——内核的直接映射区也参与 ASLR。

### 问题 22：用户能访问这些内核区吗？

不能，一个都访问不了。但**它们里面的物理页可以被共享给用户**——这是两件事。

三道防线：

**① 地址不在用户空间范围内。** 用户空间上限是 `0x0000_7FFF_FFFF_FFFF`，直接映射区在 `0xffff_8880...`，位于高半部分。

**② 页表项的 U/S 位（User/Supervisor）是 0。** 这一位为 0 表示只有内核态能访问。用户态哪怕地址算对了，一访问就触发 #PF。

**③ KPTI 页表隔离。** 用户态运行时内核那部分页表项直接从当前页表里被拿掉（见问题 24）。所以「用户访问直接映射区」不只是权限问题，而是连映射都没有。

唯一的例外是 **vDSO / vsyscall**：内核刻意把自己的少量代码映射到用户地址空间（见问题 23）。

**关键澄清：地址不能共享，物理页可以。**

```text
                    物理帧 #7（文件页 0）
                    ┌──────────────────┐
                    │   数据内容        │
                    └────┬────────┬────┘
        ┌────────────────┘        └─────────────────┐
        ▼                                           ▼
  内核线性地址                                 用户虚拟地址
  0xffff8880_1234_5000                        0x7f3a_2c00_1000
  U/S = 0（只有内核）                          U/S = 1（该进程可用）
```

两边看到的是**同一份内存，不是拷贝**。这就是 `mmap` 零拷贝、共享内存、以及「内核准备好了数据交给用户」的底层机制。

同理，`vmalloc` 分配的物理页也能分享给用户：驱动里常见 `vmalloc` 一块内存，再通过 `remap_vmalloc_range()` 映射到用户空间。

这个边界是安全课的核心。正因两个地址空间在权限上隔离，内核**不能**直接解引用用户传来的指针：

```c
/* 错的：用户传个 0xffff888000000000 就能读内核内存 */
memcpy(buf, user_ptr, n);

/* 对的：先校验地址在用户空间，再拷 */
if (copy_from_user(buf, user_ptr, n)) return -EFAULT;
```

历史上大量内核漏洞就是**某处忘了校验**（或校验写错）导致的。还有 `/dev/mem`——允许 root 把物理地址直接映射到用户空间，等于绕过整个布局，所以现代内核有 `CONFIG_STRICT_DEVMEM` 来限制它。

### 问题 23：vDSO 是什么？内核怎么把自己的代码映射给用户？

**vDSO = virtual Dynamic Shared Object，虚拟动态共享对象。**

拆开看：**SO** 是 Shared Object（共享对象），**DSO** 是 ELF 规范里对「可被动态加载的库」的正式叫法，**v** 是 virtual——因为**磁盘上并不存在这个文件**，没有对应的 `.so`，是内核在进程启动时凭空投射到地址空间里的。

整个流程四步：

**① 编译时嵌进内核映像。** 内核源码里有 `arch/x86/entry/vdso/`，单独编译成一个小 ELF，再作为数据嵌进内核映像。所以它的物理页本来就在内核映像里。

**② exec 时映射到用户地址空间。**

```text
arch_setup_additional_pages()
   → 在用户地址空间挑一个随机基址（参与 ASLR）
   → 建 VMA，用 _install_special_mapping() 挂上
   → 页表项指向内核映像里的那几个物理页
```

同一批物理页，两套地址：内核映像里有一份，用户地址空间里也有一份。

实测：

```console
$ grep -E '\[vdso\]|\[vvar' /proc/self/maps
7c4de44af000-7c4de44b3000 r--p   [vvar]          ← 16 KB 数据页
7c4de44b3000-7c4de44b5000 r--p   [vvar_vclock]   ← 8 KB 时钟专用
7c4de44b5000-7c4de44b7000 r-xp   [vdso]          ← 8 KB 代码页
```

`r-xp` 那行就是内核代码——只读可执行，用户能 `call` 进去。

**③ 用户怎么找到它。** 通过 ELF 的**辅助向量**（auxiliary vector），进程启动时内核塞在栈上的一个数组：

```console
$ LD_SHOW_AUXV=1 /bin/true | grep SYSINFO
AT_SYSINFO_EHDR:      0x7a3c75791000
```

glibc 启动时读这一项，解析出 `__vdso_gettimeofday`、`__vdso_clock_gettime` 等函数指针。

**④ 数据怎么共享。** `[vvar]` 那一页：内核写、用户读，用 seqlock 保护——用户读的时候先取一个序号，读完再取一次，如果序号变了说明内核中途改过，重读。

**为什么这么做：省掉 `syscall` 指令。** 一次 `syscall` 在开启 KPTI 的机器上要切换两套页表，代价上千个周期。取时间这种高频操作直接在本进程里执行几条指令就完了。`clock_gettime` 走 vDSO 约 20 纳秒，走系统调用约 300 纳秒。

vDSO **不能由程序创建**。用户只能从 auxv 读地址、用 `dl_iterate_phdr()` 找到它、调用里面的函数；不能指定地址、不能替换内容（页是 `r-xp`）、不能再造一个。

| 名字 | 谁创建 | 用户能创建吗 | 磁盘上有文件吗 |
|---|---|---|---|
| **vDSO** | 内核 | ✗ | ✗ |
| vsyscall 页 | 内核 | ✗ | ✗ |
| 普通共享库 `.so` | 用户/系统 | ✓ | ✓ |
| 共享内存（`shm_open` + `mmap`） | 用户 | ✓ | ✓（在 `/dev/shm`） |
| 匿名 `mmap` | 用户 | ✓ | ✗ |

还有个更老的机制 **vsyscall**：固定地址 `0xffffffffff600000`，只有 `gettimeofday`、`time`、`getcpu` 三个函数。它固定地址这点在安全上是硬伤——给攻击者一个必然存在、地址已知的可执行页。所以现代内核默认用 `vsyscall=emulate` 模式：把这一页设成不可执行，跳过去触发页错误，由内核模拟。地址还在（兼容老二进制），但没法在里面执行代码了。

### 问题 24：KPTI 是什么？为什么要拆成两套页表？

**KPTI = Kernel Page Table Isolation，内核页表隔离**，对应 2018 年初公开的 **Meltdown**（CVE-2017-5754，熔毁）。

Meltdown 的攻击链：

```text
①  用户态执行：mov rax, [内核地址]
②  CPU 乱序执行，不等权限检查结果就往下跑
③  读出的数据被装载进 cache
④  权限检查在「退休」阶段才判定失败 → 架构状态回滚
⑤  但 cache 状态不回滚 ← 关键
⑥  攻击者用 Flush+Reload 测哪一行 cache 变快 → 逐位还原内核内存
```

核心事实：权限检查**最终是生效的**，程序也确实没拿到数据。但检查完成之前的几十个周期里，数据已经被搬进缓存了，而这个副作用留了下来。所以准确说法不是「绕过权限检查」，而是**权限检查的结果被推测执行偷跑了**。

根因是：**用户态和内核态共用同一棵页表树**，内核映射在用户页表里「看得见」，只是 U/S 位不让访问。推测执行不理会这一位。

KPTI 的做法是跑两套页表：

| 什么时候 | 当前页表里有什么 |
|---|---|
| 用户态运行时 | 只有用户空间映射 + 极少量必需的入口代码 |
| 进入内核时 | 切换到完整页表，内核映射全在 |

AMD 的处理器不受 Meltdown 影响（权限检查在流水线更早阶段完成，越权数据根本不会被加载进缓存），所以 `pti=auto` 在 AMD 上不开。

顺带区分 Meltdown 和 Spectre：

| | Meltdown | Spectre |
|---|---|---|
| 利用的是 | 硬件权限检查的时序缺陷 | 受害者程序自己的推测执行 |
| 是否真越权 | 是 | 否（诱导合法代码越界读） |
| 软件能挡吗 | 能（KPTI 很有效） | 很难 |
| 影响面 | 主要 Intel | 几乎所有现代 CPU |

### 问题 25：开 KPTI 后每次 `syscall` 都换 CR3 吗？为什么慢？

**是的，每次用户态↔内核态切换都要换页表。** 但「换」的方式有讲究。

**两张 PGD 是相邻的两页。** 内核把同一个进程的 user PGD 和 kernel PGD 分配在相邻的两个物理页里，用 CR3 的**第 12 位**区分：

```text
kernel PGD 的物理地址     0x...0000  （bit12 = 0）
user   PGD 的物理地址     0x...1000  （bit12 = 1）  ← 只差一页
```

所以「切 CR3」不是重新加载一个完全不同的地址，而是清掉或设上这一位。

**切换发生在进入内核之后的头几条指令。** 因为 `syscall` 执行时 CPU 还没换页表，如果内核入口代码不在用户页表里，第一条指令就缺页了。所以内核在用户页表里也保留了一小块：

```text
用户态执行 syscall
   ↓
落到 entry trampoline        ← 这段代码在用户页表里也可执行
   ↓
执行 SWITCH_TO_KERNEL_CR3    ← 这里才真正换页表
   ↓
跳到完整的内核代码
   ↓
（返回时）SWITCH_TO_USER_CR3
```

例外：内核态内部执行不切；一次进入后连续处理多个事件只在第一次切；CPU 没有 `X86_FEATURE_PTI` 时这些宏编译成空操作。

**性能代价全在 TLB。** 三层原因：

1. **写 CR3 是序列化操作**，清掉流水线，CPU 重新取指，几十个周期。
2. **换页表会让 TLB 失效。** TLB 命中约 1 个周期，未命中要查 4 级页表。
3. **系统调用密集的负载最惨**，一次 `syscall` 要切两次（进、出）。

| 负载类型 | 典型损失 |
|---|---|
| 纯计算（几乎不调系统调用） | < 5% |
| 普通应用 | 5%–15% |
| 数据库、网络服务器（大量小 I/O） | 20%–30% |

缓解手段是 **PCID**（Process Context Identifier，进程上下文标识）：12 位，`CR4.PCIDE = 1` 时 CR3 的低 12 位被解释为标签而不是地址。KPTI 的分配方案很省：

```text
kernel PCID = mm->context.pcid           （bit 11 = 0）
user   PCID = kernel PCID | (1 << 11)    （bit 11 = 1）
```

每个进程占用**一对**标签，靠第 11 位区分「这套页表给用户态用还是给内核态用」。这样切 CR3 时 TLB 里两套翻译可以共存，不必全刷。

代价是**标签数量腰斩**：硬件总共 4096 个 PCID，成对占用后只够约 2048 个进程。超了 Linux 就轮转分配，一轮用完触发一次全局 TLB 刷新。

其他缓解：把最开头的入口代码（trampoline）也放进用户页表；`cpu_entry_area` 把每 CPU 的入口栈、TSS、GDT 映射在固定位置，两套页表里都有。以及——**`vDSO`**：不进内核就不用付这个代价。KPTI 时代 `vDSO` 的价值比原来大得多。

## 第六部分：地址为什么不能写死

### 问题 26：ASLR 怎么做到的？

**ASLR = Address Space Layout Randomization，地址空间布局随机化。** 本质是在 `execve` 时给每个区域挑一个起点，而不是随机化内存内容。

因为代码字节、`.data` 内容、指令里的位移都不变，变的只是「这段内容被映射到哪个虚拟地址」。

`execve` 走 `load_elf_binary()`，内核此时做三次抽取随机数。用算术表达就是三行：

```text
主程序放哪  = 基准位置 − (随机数① mod 2^28) × 4096
栈顶在哪    = 地址空间顶端 − (随机数② mod 2^22) × 4096
动态库放哪  = 基准位置 − (随机数③ mod 2^28) × 4096
```

每个随机数乘 4096（一页大小），得到一个字节偏移，再从固定基准往下减。

| 管什么 | 随机多少位 | 乘 4096 之后的范围 |
|---|---|---|
| 主程序映像 | 28 位（可调到 32） | 1 TB（32 位时 16 TB） |
| 动态库 | 28 位 | 1 TB |
| 栈顶 | 22 位 | 17 GB |

实测（同一个 PIE 程序跑两次，全局变量的地址）：

```console
PIE 第一次：0x59d2ae6d8010
PIE 第二次：0x60385e51f010     ← 每次不同

非 PIE 两次：0x404018
非 PIE 两次：0x404018          ← 完全一样
```

前置条件有两个：`randomize_va_space` 开着（`/proc/sys/kernel/randomize_va_space`，本机是 `2`），且程序不是 `ET_EXEC`。

**动态库不归内核直接管，归 `ld.so` 管。** 但 `ld.so` 也没自己算随机数，它只是调用 `mmap(NULL, …)`，把地址参数传 0 = 「内核你挑一个」。于是每个库都被内核的同一套随机 mmap 区逻辑分到不同位置。实测两次运行 `libc` 的基址：

```console
76497b400000-76497b428000  libc.so.6
7b468ea00000-7b468ea28000  libc.so.6
```

内核自己也有 KASLR：编译时内核是 PIE，引导阶段 `choose_random_location()` 选一个物理加载地址，同时随机虚拟偏移；模块加载区、vmalloc 区、直接映射区各自随机。

**什么时候 ASLR 直接失效：**

| 情况 | 原因 |
|---|---|
| `fork` 出来的子进程 | 子进程复制父进程的 `mm_struct`，布局完全相同。ASLR 只在 `execve` 时生效 |
| `setarch -R` / `personality(ADDR_NO_RANDOMIZE)` | 内核显式跳过随机化 |
| `randomize_va_space = 0` | 全局关闭 |
| 主程序是 `ET_EXEC` | 主程序和堆不动 |
| 熵不足 | 早期虚拟机/嵌入式启动时熵池空，随机数可预测 |

### 问题 27：页表是「被改」还是「被重建」？

**是重建。** 这个说法容易含糊，值得说准。

```text
execve 开始
  ↓
销毁旧进程的整套内存结构（连同页表）
  ↓
抽三个随机数 → 决定主程序、栈、mmap 区的起点
  ↓
按这些起点建立新的 VMA
  ↓
建立页表项（这时虚拟地址才真的对应上物理页）
  ↓
数据按需从磁盘读入
```

所以不存在「先摆在固定位置，再改表把它挪走」这个动作。页表是**按随机地址建出来的**。

在页表上落地时，改的是虚拟地址那一列：

| 加载前 | | 加载后（抽到 +0x5000） |
|---|---|---|
| `0x400000` → 物理页 100 | | `0x405000` → 物理页 100 |
| `0x401000` → 物理页 101 | | `0x406000` → 物理页 101 |
| `0x402000` → 物理页 102 | | `0x407000` → 物理页 102 |

**左边一列全加了 0x5000，右边一列一个都没变。** 物理内存没搬，内容没复制，只是虚拟地址那一列整体平移。

真正会在运行时修改页表的，是另一批操作：

| 操作 | 对页表做了什么 |
|---|---|
| 缺页 | 填入一个新的页表项 |
| `mprotect` | 改权限位 |
| `mmap` / `munmap` | 增删页表项 |
| `mremap` | 把映射挪到别处（这个是真「改」） |
| swap 换入换出 | 改「在不在内存」的标志 |
| `fork` | 复制整张页表 |

最后一行是关键对照：`fork` 出来的子进程页表是**复制**的，所以地址和父进程完全一样——ASLR 不生效。这恰好证明 ASLR 是「建表那一刻」决定的。

### 问题 28：RIP 相对寻址是什么？

x64 允许指令在引用数据时使用相对于 `RIP` 的地址。x86-64 之前访问全局变量只能写死绝对地址：

```asm
movl  $0x401000, %eax      # 绝对地址，链接时就定了
```

开了 ASLR 后，程序映像的加载基址每次运行都随机，`0x401000` 就不指向那个全局变量了。x86-64 改成：

```asm
movq  0xf79(%rip), %rax    # 从 RIP 往前数 0xf79 个字节
```

因为 ASLR 只让程序整体平移，**代码和它自己的数据之间的相对距离不变**：

```text
基址 = 0x400000
    0x400080  ← 指令开始
    0x400087  ← 下一条指令（RIP 指向这里）
    0x401000  ← 全局变量 g
    Δ = 0x401000 − 0x400087 = 0xF79

基址 = 0x405000（整体 +0x5000）
    0x405080  ← 指令开始
    0x405087  ← RIP 指向这里
    0x406000  ← g 也一起平移了
    Δ = 0x406000 − 0x405087 = 0xF79   ← 没变
```

**最容易踩的坑：`RIP` 指向「下一条指令」，不是本条指令的地址。** 上面那 7 字节就是差值的来源——如果误以为从「本条指令开头」算，会得到 `0xF80`，差 1。

还有一点：`RIP` **不是通用寄存器**。x86-64 的通用寄存器只有 16 个（`RAX` `RBX` `RCX` `RDX` `RSI` `RDI` `RBP` `RSP` 加 `R8`–`R15`），`RIP` 属于指令指针寄存器，不能当 `mov` 的目的操作数，只能靠 `lea rax, [rip]` 间接取。它只由跳转、调用、返回、中断、异常自动修改。

32 位时代没有 `(%eip)` 这种寻址方式，也没有指令能把 `EIP` 读出来，所以 32 位的位置无关代码只能靠 `call next; next: pop %ebx` 这种取巧手法。

`RIP` 相对位移是 32 位有符号立即数，范围 ±2 GB。所以同一个模块内部的全局变量直接找到，跨模块（另一个 `.so` 里的函数或变量）要先经过 GOT（Global Offset Table，全局偏移表）再间接跳转——`call printf@plt` 走的就是这条路径。

### 问题 29：PIC 和 PIE 是什么？

**PIC = Position Independent Code，位置无关代码**：机器码里不含任何绝对地址，可以被加载到任意虚拟地址而不需要修改任何一个字节。

它解决一个很具体的问题：**一个 `.so` 的物理页要被几百个进程共享，但每个进程的加载基址都不同。**

没有 PIC，每个进程加载 `libc.so` 时都得把代码里所有绝对地址改写成自己那份基址——于是代码页必须可写，一写就 COW，物理内存里变成几百份副本，共享彻底失效。

**PIE = Position Independent Executable，位置无关可执行文件**：把**主程序**也编译成这种形式。

| | PIC | PIE |
|---|---|---|
| 说的是 | **代码本身**没有绝对地址 | **整个可执行文件**可以被搬到任意地址 |
| 谁需要 | 共享库**必须** | 主程序（可选，但强烈建议） |
| 怎么开 | `-fPIC` / `-fPIE` | 链接时 `-pie` |

链接结果的 ELF 类型是关键：

| ELF Type | 含义 | ASLR 效果 |
|---|---|---|
| `ET_EXEC` | 链接时地址就定死了（通常 `0x400000`） | **主程序地址固定，ASLR 对它无效** |
| `ET_DYN` | 没有固定地址，加载时才决定 | 主程序随机化 ✓ |

本机实测（同一份 `t.c`）：

```console
$ gcc t.c -o t_def && gcc t.c -no-pie -o t_nopie
$ readelf -h t_def   | grep Type
  Type:  DYN (Position-Independent Executable file)
$ readelf -h t_nopie | grep Type
  Type:  EXEC (Executable file)
$ gcc -v 2>&1 | grep -o -- --enable-default-pie
--enable-default-pie
```

为什么要 PIE：不开时 ASLR 依然在保护 `.so`、栈、堆，但**主程序那个最大的映像被漏掉了**。而 ROP 用的 gadget 主要在主程序里，主程序地址固定就等于 gadget 地址写死，**不需要任何信息泄露**。堆又紧跟在主程序后面，所以堆地址也基本可预测。

三个常见误解：

1. **「PIE 意味着程序里没有任何绝对地址」**：GOT 表项里存的就是绝对地址，运行时由动态链接器填。PIE 保证的是**代码段里不含立即数形式的绝对地址**。
2. **「编译加了 `-fPIE` 就是 PIE 了」**：还要链接时加 `-pie`。只加前者，产物仍是 `ET_EXEC`。
3. **「有 PIE 就绕不过 ASLR」**：一个信息泄露漏洞照样能把地址问出来。

代价很小：跨模块调用多一层 GOT/PLT 间接跳转，通常损失 0–3%。32 位上代价明显得多（`-fPIC` 要保留 `%ebx` 当 GOT 基址），x86-64 有 `RIP` 相对寻址后这个负担消失了。

### 问题 30：这四个概念是什么关系？

它们**不在同一个层面上**，是一条链上的四个环节。

```
① 机制层      RIP 相对寻址（CPU 的指令编码规范）
                  ↓ 提供「不依赖基址」的寻址方式
② 代码层      PIC        （编译器的产出策略）
                  ↓ 代码既然不需要基址，链接器就敢把文件标成可搬运
③ 文件层      PIE        （ELF 头里的一个字段：Type: DYN）
                  ↓ 内核看到 DYN 才敢随机放
④ 运行时      ASLR       （内核/ld.so 每次 exec 的决定）
                  ↓
⑤ 安全效果    gadget 地址不可预测 → 攻击者必须先找信息泄露
```

用本机实测的两条指令佐证「差别不在指令本身」：

```console
PIE 版   main @ 0x1149（偏移，基址待定）
  48 8d 15 b8 2e 00 00   lea 0x2eb8(%rip),%rdx   # 4010 <g>

非 PIE  main @ 0x401136（绝对）
  48 8d 15 d3 2e 00 00   lea 0x2ed3(%rip),%rdx   # 404018 <g>
```

**两边都是 `lea 位移(%rip)`，编码方式完全一样。** 说明 `RIP` 相对寻址不是「PIE 专用的特殊指令」，它是 x86-64 上访问全局数据的默认写法。真正的差别只有两处：

```console
① 文件头里的一个字段（这是 PIE 的全部内容）
   PIE → Type: DYN      非 PIE → Type: EXEC

② 运行时全局变量的地址（这是 ASLR 的全部内容）
   PIE 两次：0x59d2ae6d8010 / 0x60385e51f010   ← 不同
   非 PIE ：0x404018       / 0x404018          ← 相同
```

反过来记更清楚：

- 没有 ASLR，PIC/PIE 只是「能搬但没人搬」
- 没有 PIE，ASLR 搬不动主程序
- 没有 PIC，PIE 搬了也是错的
- 没有 RIP 相对寻址，PIC 在 x86 上要靠 `call/pop` 硬凑，代价是多占一个寄存器

顺带一个**必须澄清的坑**：讲义里 `.data`、`.bss`、`.rodata`、栈、堆那些「段」，和 IA-32 的硬件段**不是一回事**。

| | IA-32 硬件段 | ELF 里的 `.text` / `.data` |
|---|---|---|
| 谁定义 | CPU（GDT / LDT 描述符） | 链接器（ELF 节） |
| 作用 | 地址翻译 + 权限检查 | 安排变量放在哪、加载时怎么映射 |
| 一个程序能有几个 | 最多 16383 个 | 固定若干个 |

在 Linux x86-64 上，所有 ELF 段都装在**同一个**平坦硬件段里，彼此之间只靠页表权限区分。名字撞了，概念不相干。

## 第七部分：超过物理内存之后

### 问题 31：用了超过物理内存的虚拟地址空间会怎样？

要分三种情况，行为完全不同。本机配置是物理内存 24 GB、swap 6 GB。

**情况 A：只占地址空间，不访问。**

```console
1 GB   → 成功（物理占用 0）
1 TB   → 成功（物理占用 0）
32 TB  → 成功（物理占用 0）
64 TB  → 成功（物理占用 0）
```

`mmap` 一块 64 TB 的匿名区域，**物理内存一个字节都没占**。成本只有一个 VMA（几十字节），页表项等真访问时才分配。这是设计的正常状态。

**情况 B：真去访问，物理内存不够。** 内核按顺序处理：

```text
① 回收干净的文件页缓存   —— 直接丢弃（磁盘上有副本）
② 回收脏页              —— 先写回磁盘，再丢
③ 匿名页换出到 swap      —— 写入 swap，页表项标记「在 swap 里」
④ 都不够 → OOM Killer   —— 挑一个进程 SIGKILL
```

③ 是虚拟内存的核心。匿名页在磁盘上没有副本，不能像文件页那样丢弃，只能换到 swap。再访问被换出的页会触发**主缺页**，从 swap 读回来。

④ 的表现很暴力：

```text
Out of memory: Killed process 12345 (myprogram)
```

没有异常、没有返回值，进程直接消失。选择谁被杀看 `oom_score`（按内存占用、是否 root 等调整）。

**情况 C：分配之前就被拒绝。** 很多限制在 `mmap`/`malloc` 阶段就把它挡住了（详见问题 33）。

### 问题 32：overcommit 是什么？为什么报错来得晚？

这是 Linux 内存管理最容易踩的坑。内核记账分两本：

```console
$ grep -E 'CommitLimit|Committed_AS' /proc/meminfo
CommitLimit:    18350920 kB    ← 承诺上限（物理 + swap 的一部分）
Committed_AS:    6411168 kB    ← 已经承诺出去的
```

`mmap`/`malloc` 时只增加**承诺**（commit），不分配物理页；真写内存时才分配。

三种策略（`vm.overcommit_memory`）：

| 值 | 含义 | 后果 |
|---|---|---|
| `0` | 启发式（默认）：大致允许，明显过分就拒 | 大请求会立即 `ENOMEM` |
| `1` | 总是允许 | `mmap` 几乎不失败，但之后可能被 OOM 杀掉 |
| `2` | 严格：不能超过 `物理 × ratio% + swap` | 最可预测，但对 `fork`/COW 不友好 |

同一台机器上的实测对比：

```console
1 GB   不带 NORESERVE → 成功
32 TB  不带 NORESERVE → 失败 (ENOMEM)     ← 承诺时就被拒
32 TB  带 NORESERVE   → 成功              ← 跳过承诺记账
1 TB   不带 NORESERVE → 失败 (ENOMEM)
```

`MAP_NORESERVE` 就是「别给我记承诺」。MySQL、Redis 这类程序常被建议调 `overcommit_memory=1`，就是因为它们会预先 `malloc` 一大块。

**这个设计的副作用**：程序 `malloc` 成功了，`memset` 到一半被 OOM 杀掉——看起来像「无 bug 的程序莫名退出」。而 `=1` 会让这种情况更常见。`=2`（严格）能让 `malloc` 当场失败、便于处理，但会让 `fork` 大进程直接失败。

`fork` 为什么依赖它：`fork` 后父子共享页面，理论上最多要多一倍的物理内存，但实际几乎不会真复制（COW）。如果按最坏情况记账，`fork` 一个大进程就永远失败。

### 问题 33：`ulimit` 限制的是地址空间长度吗？

`ulimit` 是 shell 内建的接口，背后是十几种不同的资源限制，各自管完全不同的东西：

| 选项 | 资源 | 限制什么 |
|---|---|---|
| `-v` | `RLIMIT_AS` | **地址空间总量** |
| `-d` | `RLIMIT_DATA` | 数据段（`brk` + 匿名私有映射） |
| `-s` | `RLIMIT_STACK` | 栈最大能长到多大 |
| `-f` | `RLIMIT_FSIZE` | 单个文件能写多大 |
| `-n` | `RLIMIT_NOFILE` | 打开文件描述符个数 |
| `-u` | `RLIMIT_NPROC` | 该用户的进程/线程数 |
| `-c` | `RLIMIT_CORE` | core dump 文件大小 |
| `-t` | `RLIMIT_CPU` | CPU 时间（秒） |
| `-l` | `RLIMIT_MEMLOCK` | 能 `mlock` 锁定的内存 |
| `-m` | `RLIMIT_RSS` | **Linux 直接忽略**（历史遗留） |

`ulimit -v` 的确管用户地址空间，但**「长度」这个词不准确**：地址空间不是一段连续区间，是一堆 VMA 的集合，`RLIMIT_AS` 限制的是这些 VMA 的**字节数之和**，不是某一段的长度。

| 算进去 | 不算 |
|---|---|
| 代码段、`.data`、`.bss` | 内核空间的映射 |
| 堆（`brk`） | 页表本身占的内存 |
| 栈 | 实际占用的物理内存 |
| 所有 `mmap` 区（含**只读文件映射**） | |

本机：`ulimit -v` 是 `unlimited`，`ulimit -s` 是 8192 KB。

四个容易踩的坑：

1. **只读文件映射也计入。** 设 `ulimit -v 1048576`（1 GB）后，`mmap` 一个 2 GB 的 `.so` 会失败，哪怕物理内存空着大半。
2. **`MAP_NORESERVE` 对它无效。** 那个标志只影响承诺记账，不影响地址空间计数。
3. **`ulimit -m` 是空操作。** Linux 从来不实现 `RLIMIT_RSS`。
4. **soft / hard 两层。** `ulimit -S` 是软限制（进程自己可以调低、可以调高到硬限制），`ulimit -H` 是硬限制（只有 root 能提高）。

除了 `ulimit`，还有几个不同维度的限制：

| 限制 | 管什么 | 记账对象 | 失败表现 |
|---|---|---|---|
| `vm.overcommit_memory` | 全系统允许承诺多少 | 承诺 | `mmap` 返回 `ENOMEM` |
| `RLIMIT_AS` | 单进程地址空间总量 | `VmSize` | `ENOMEM` |
| `vm.max_map_count` | 单进程 **VMA 个数** | VMA 计数 | `ENOMEM` |
| cgroup `memory.max` | 一个 cgroup 的实际物理占用 | RSS + 页缓存 | **被 OOM 杀掉** |

四个关键区别：**记账对象不同**（承诺 / 虚拟大小 / 实际驻留是三种账本）、**失败时机不同**（分配时返回 `ENOMEM`，程序能处理；访问时被 `SIGKILL`，程序无法处理）、**作用范围不同**（全局 / cgroup / 进程 / VMA 计数）、**`max_map_count` 和内存无关**（一个 100 GB 的映射只算 1 个，十万个 4 KB 的小映射才撞上限——`glibc` 多 arena、JIT 编译器容易踩）。

### 问题 34：RSS 是什么？为什么不能用来比较内存占用？

**RSS = Resident Set Size，常驻集大小**：这个进程**此刻真正驻留在物理内存里**的页的总字节数。对应 `ps` 的 `RSS` 列、`top` 的 `RES` 列、`/proc/<pid>/status` 的 `VmRSS`。

它由三部分组成：

```text
VmRSS = RssAnon + RssFile + RssShmem
```

本机实测（当时那个 shell）：

```console
VmRSS:       2528 kB
RssAnon:      176 kB    ← 匿名页（堆、栈）
RssFile:     2352 kB    ← 文件页（二进制、libc 的代码和只读数据）
RssShmem:       0 kB
               ─────
       176 + 2352 + 0 = 2528  ✓
```

和 `VmSize` 的区别：

| | `VmSize`（`ulimit -v` 管它） | `VmRSS` |
|---|---|---|
| 是什么 | 地址空间总量 | 驻留物理页 |
| 是否等于物理内存占用 | 不是，可能远大于 | 是（但有重复计算，见下） |
| `mmap` 100 GB 不访问 | 涨 100 GB | **不变** |
| 典型值 | 几 GB 到几 TB | 几 MB 到几 GB |

**关键缺陷：共享页被重复计入。** 同一个 `libc.so` 被 200 个进程映射，那几 MB **会分别算进每个进程的 RSS**。所以把所有进程的 RSS 加起来常常远超物理内存总量。

所以有两个修正指标：

| 指标 | 含义 |
|---|---|
| **PSS**（Proportional Set Size） | 共享页按「共享的进程数」平均分摊 |
| **USS**（Unique Set Size） | 只属于这个进程、不和别人共享的页 |

实测对比（同一个进程）：

```console
Rss:            2504 kB      ← 常被误读成「占了多少内存」
Pss:             430 kB      ← 实际应该分给它的份额
Shared_Clean:   2144 kB      ← 绝大部分是和其他进程共享的
Private_Dirty:   180 kB      ← 真正独占且改过的
```

**RSS 2504 kB，PSS 只有 430 kB**——差了六倍。这就是为什么用 RSS 判断「哪个进程占内存多」会得出错误结论。

OOM Killer 打分主要就看 RSS（加上 `oom_score_adj`）。所以「谁被杀了」很大程度取决于 RSS 排行，而 RSS 里包含共享页——一个只映射了共享库的进程也可能因为 RSS 偏高被选中。

六个指标对齐：

| 名字 | 出现的地方 | 含义 |
|---|---|---|
| `VmSize` / `VIRT` | `status` / `top` | 地址空间总量（`ulimit -v` 管它） |
| `VmRSS` / `RES` | 同上 | 驻留物理页（共享页重复计入） |
| `RssAnon` / `RssFile` / `RssShmem` | `status` | RSS 的三个组成部分 |
| `Pss` | `smaps_rollup` | 按共享比例分摊后的真实占用 |
| `VmSwap` | `status` | 被换出到 swap 的页 |
| `Committed_AS` | `/proc/meminfo` | 全系统已承诺、尚未兑现的量 |

## 附录 B：实测环境与观察命令

实测环境：x86-64，四级页表，物理内存 24 GB，swap 6 GB，GCC 默认 `--enable-default-pie`，`randomize_va_space = 2`，`ulimit -s = 8192 KB`。

**地址空间布局**

```bash
cat /proc/self/maps                        # 这个进程的所有 VMA
head -6 /proc/self/maps                    # 主程序那几段
grep -c . /proc/<pid>/maps                 # VMA 条数
```

**页表与页缓存**

```bash
grep -E 'Cached|PageTables|AnonPages|Shmem' /proc/meminfo
grep -E 'VmSize|VmRSS|RssAnon|RssFile' /proc/<pid>/status
grep -E 'Rss|Pss|Shared_Clean' /proc/<pid>/smaps_rollup
```

**mmap 懒加载**

```bash
# 映射一个大文件后先看 Rss，再逐页访问，Rss 会一页页涨
cat /proc/<pid>/smaps | grep -A5 bigfile
grep -E 'minflt|majflt' /proc/<pid>/stat    # 次缺页 / 主缺页计数
```

**PIE / ASLR**

```bash
readelf -h ./a.out | grep Type             # DYN = PIE，EXEC = 非 PIE
file ./a.out                               # "pie executable" 或 "executable"
cat /proc/sys/kernel/randomize_va_space     # 2 = 全开
setarch -R ./a.out                         # 临时关掉 ASLR
ldd ./a.out                                # 看各库基址（多跑几次会变）
```

**内存压力与限制**

```bash
free -h                                    # buff/cache 解释了 free 很小
grep -E 'Commit|Swap' /proc/meminfo        # 承诺账本
vmstat 1                                   # si/so 列看 swap 换入换出
dmesg | grep -i 'killed process'           # 谁被 OOM 杀了
cat /proc/sys/vm/overcommit_memory
cat /proc/sys/vm/max_map_count
ulimit -a
```

**内核侧**

```bash
dmesg | grep -iE 'Memory:|page_offset'     # 启动时的内存布局记录
ls /sys/kernel/debug/kernel_page_tables    # 需要 debugfs + root
```
